###### 1. Long-Term Product Identity
**Target Product:** A **complete single-woodland 2D CCF simulator** sharing one forestry engine with the 3D Unity game.
- **Complement to 3D (Not a Duplicate):** 3D Unity is for walking through a woodland, looking up at crowns, and experiencing Irish scenarios at eye level. The 2D simulator is for bird's-eye silviculture, stepping through decades quickly, managing larger multi-lane woodlands, experimenting with custom woods, testing new tree species, and importing real-world map and drone/LiDAR data.
- **One Complete Woodland First:** Making one woodland genuinely satisfying and complete to manage comes before side-by-side comparison modes (comparing two woods side-by-side is parked for the final stage).
- **Playable Gameplay First (2026-11-28 Priority):** With **Playable Milestone 1**, **Map-First Menu & Lenses Upgrade**, and all **4 of 4** post-Milestone 1 engine halves combined cleanly onto `integration/2d-sim` (`f4dee802`), keep active delivery moving across Part 2 screen wiring, **Year-30 Deep-History Payload Compaction**, **Full Custom Woodland Builder (Part 1)**, **Open-Source Satellite Map Plug (MapLibre — Part 1)**, and **Natural Old-Age Tree Death & Smooth Late-Life Growth (Part 1)** in parallel—with **Standing Deadwood (Snags) & Gradual Decay (Playable Milestone 9 — Track B)** design-locked and held for later launch while **Tracks C & D** queue up for read-only 3D-reuse research.

###### 3. Core Guardrails (Plain English)
1. **The screen does zero forestry math:** Every map and panel only displays what the pure-.NET forestry engine calculates and sends player actions back.
2. **Maximise safe parallel coding lanes; combine one at a time:** There is no arbitrary cap on parallel coding lanes—run 2, 3, 4, 5, or more non-overlapping coding lanes simultaneously whenever independent work is ready. Unbundle small shared wiring pieces into integrator follow-ups so larger features start coding immediately in isolated folders. One integrator controls shared wiring files and combines reviewed work one piece at a time using minimum necessary checks.
3. **Minimum Necessary Testing — Strict Verification Diet (Locked 2026-11-27):** Always run the smallest set of tests that proves the specific change is safe—never default to multi-hour full sweeps on routine feature work or routine combines. Routine combines run only a clean build, fast core/baseline checks, file-boundary checks, and the feature's own targeted tests (~2–5 minutes). Skip browser tests completely when no screen files changed, and run only the touched area's browser check when screen files did change. Never run safety-script self-tests (`selftest.sh`) unless the safety script itself was edited, and never re-run suites that already passed on the same unchanged code. Reserve full integrated browser/regression sweeps strictly for completed Playable Milestones, releases, or concrete blockers, while keeping honest status distinctions (IMPLEMENTED / REVIEWED / INTEGRATED / VERIFIED / ACCEPTED).
4. **Flat metres inside the engine:** Even when real satellite maps or elevation/contour layers are added later, all tree distances, crowns, and ground squares stay in flat local metres so map projections never warp tree growth.
5. **Open-source map tech only:** Use open-source MapLibre (zero tokens, zero per-load fees, works offline) instead of paid Mapbox, separating the open-source renderer cleanly from satellite imagery licensing.
6. **Clear line between real measurements and simulation:** Imported real-world woodlands always separate what was actually measured at Year 0 from what the simulator predicts in future years.
7. **Clean Live UI, Honest Documentation & CCF-Faithful Choices (Updated 2026-11-28):**
   - **Keep the live UI clean and natural:** Use plain, everyday forestry wording on screen (*"Died of old age"*, *"Standing deadwood"*, *"Heavy deer pressure"*). Keep `[C]`/`[E]` tags, *"gameplay calibration"* labels, and academic disclaimers strictly inside documentation, specs, and code comments—never cluttering the live player interface. Only show special status notices on screen when they directly govern what the player can do (such as **"Survey inspection mode — Year 0"** explaining why Advance Time is disabled, or **"Not Recorded"** where older data genuinely does not exist) or where a map tile source legally requires attribution.
   - **CCF-faithful & player-led:** Clearfelling is never offered in a Continuous-Cover Forestry simulator, and the simulator never grades players against one "right" thinning cut.
8. **Protect the 3D game and old baselines:** All 2D work stays completely separate from Unity `Assets/`, `Compact30`, `Legacy40`, `Enlarged80`, `Reference Future v1`, single-area web files, and all 9 frozen simulation fingerprints. `main` stays untouched (`bdeb6a32`).
9. **Model routing, effort limits & backup builders:** Coordinating, building, and independent reviewing stay strictly separate (the coordinator never writes code, specs, or reviews; independent reviews always run on a separate, fresh thread from the builder). Neither Opus 5.5 nor Neon starts above `high` effort (escalation allowed only if `high` fails). If Neon runs out of tokens during implementation, it may hand off building to Opus 5.5 or Sonnet 6.1 (`6.1` active now; `6.2` future option). If **GPT-6.2 Sol** stops on a delegated authority or verification check, the bounded fallback goes to **GPT-6.1 Sol** (not Astra).
10. **Separate tooling track & laptop worker setup (2026-11-27):** **SKILLS-017E** (secure owner-confirmation prototype in `myT3skills`) stays strictly independent and must never delay simulator gameplay. Desktop-to-laptop T3 execution is verified working (ignore misleading T3 Connect status flags unless an actual failure occurs), and external SSD **ZX20** (exFAT, 235 GB free; `/media/jer/ZX20/ccf-2d-lanes` and `/media/jer/ZX20/ccf-2d-cache`) is ready for isolated laptop 2D lanes while keeping the bare Git store, Unity, and single-integrator merges strictly on the desktop.
11. **Keep GitHub synced with Strategy updates automatically (Locked 2026-11-27):** Because the Strategy Manager chat has no direct GitHub write access, every update to `2D_Simulator_Strategic_Roadmap.md` (or other living 2D strategy docs) in this notebook automatically bundles a single-writer **GitHub Sync** step into the next outgoing packet to an implementing or integrating agent so the updated file is committed onto `integration/2d-sim` (`Docs/Handoffs/MultiRack-Simulation-20261116/2D_Simulator_Strategic_Roadmap.md`). Never assign the same doc to multiple parallel lanes at once, and keep `main` untouched. *(Sync status as of 2026-11-28: GitHub is synced at `v1.22` via commit `f4dee802`; bundle complete untruncated `v1.27` into the next single-writer integrator combine.)*
