#### 1. Long-Term Product Identity
**Target Product:** A **complete single-woodland 2D CCF simulator** sharing one forestry engine with the 3D Unity game.
* **Complement to 3D (Not a Duplicate):** 3D Unity is for walking through a woodland, looking up at crowns, and experiencing Irish scenarios at eye level. The 2D simulator is for bird's-eye silviculture, stepping through decades quickly, managing larger multi-lane woodlands, experimenting with custom woods, testing new tree species, and importing real-world map and drone/LiDAR data.
* **One Complete Woodland First:** Making one woodland genuinely satisfying and complete to manage comes before side-by-side comparison modes (comparing two woods side-by-side is parked for the final stage).
* **Playable Gameplay First (2026-11-27 Priority):** With the **Soil Moisture Table & Native Tree Profile Cards** and **Real-World Woodland Importer** foundations now combined cleanly onto `integration/2d-sim`, shift focus squarely to **player-facing playable forestry milestones** rather than more isolated components, redundant re-testing, or infrastructure work.

#### 3. Core Guardrails (Plain English)
1. **The screen does zero forestry math:** Every map and panel only displays what the pure-.NET forestry engine calculates and sends player actions back.
2. **Maximise safe parallel coding lanes; combine one at a time:** There is no arbitrary cap on parallel coding lanes—run 2, 3, 4, 5, or more non-overlapping coding lanes simultaneously whenever independent work is ready. Unbundle small shared wiring pieces into integrator follow-ups so larger features start coding immediately in isolated folders. One integrator controls shared wiring files and combines reviewed work one piece at a time.
3. **Proportionate verification & reduced overhead (Added 2026-11-27):** Match testing to actual risk. Use targeted feature/fix tests plus a clean merge, build, and narrow combined-candidate check when an isolated component is already independently reviewed. Reserve full integrated regression suites for playable milestones, releases, concrete risks, or mandatory gates. Never reopen closed qualification or repeatedly test test-infrastructure without a concrete blocker, while keeping honest status distinctions (`IMPLEMENTED` / `REVIEWED` / `INTEGRATED` / `VERIFIED` / `ACCEPTED`).
4. **Flat metres inside the engine:** Even when real satellite maps are added later, all tree distances, crowns, and ground squares stay in flat local metres so map projections never warp tree growth.
5. **Open-source map tech only:** Use open-source MapLibre (zero tokens, zero per-load fees, works offline) instead of paid Mapbox.
6. **Clear line between real measurements and simulation:** Imported real-world woodlands always separate what was actually measured at Year 0 from what the simulator predicts in future years.
7. **Honest labels, CCF-faithful & player-led choices:** Gameplay calibrations and small-woodland money caveats stay clearly labelled, clearfelling is never offered in a Continuous-Cover Forestry simulator, and the simulator never grades players against one "right" thinning cut.
8. **Protect the 3D game and old baselines:** All 2D work stays completely separate from Unity `Assets/`, `Compact30`, `Legacy40`, `Enlarged80`, `Reference Future v1`, single-area web files, and all 9 frozen simulation fingerprints. `main` stays untouched (`bdeb6a32`).
9. **Model routing, effort limits & backup builders:** Coordinating, building, and independent reviewing stay strictly separate (the coordinator never writes code, specs, or reviews; independent reviews always run on a separate, fresh thread from the builder). Neither Opus 5.5 nor Neon starts above high effort (escalation allowed only if high fails). If Neon runs out of tokens during implementation, it may hand off building to Opus 5.5 or Sonnet 6.1 (6.1 active now; 6.2 future option). If **GPT-6.2 Sol** stops on a delegated authority or verification check, the bounded fallback goes to **GPT-6.1 Sol** (not Astra).
10. **Separate tooling track & laptop worker setup (2026-11-27):** **SKILLS-017E** (secure owner-confirmation prototype in `myT3skills`) stays strictly independent and must never delay simulator gameplay. Desktop-to-laptop T3 execution is verified working (ignore misleading T3 Connect status flags unless an actual failure occurs), and external SSD **ZX20** (exFAT, 235 GB free; `/media/jer/ZX20/ccf-2d-lanes` and `/media/jer/ZX20/ccf-2d-cache`) is ready for isolated laptop 2D lanes while keeping the bare Git store, Unity, and single-integrator merges strictly on the desktop.
11. **Keep GitHub synced with Strategy updates (Added 2026-11-27):** Because the Strategy Manager chat has no direct GitHub write access, every update to `2D_Simulator_Strategic_Roadmap.md` (or other living 2D strategy docs) must be paired with a **GitHub Sync** note to the 2D Delivery Manager so **one** designated T3 Code agent or the Single Integrator commits the updated file onto `integration/2d-sim` (`Docs/Handoffs/MultiRack-Simulation-20261116/2D_Simulator_Strategic_Roadmap.md`). Never assign the same roadmap file to multiple parallel coding lanes at once (to avoid merge clashes), and keep `main` untouched.
