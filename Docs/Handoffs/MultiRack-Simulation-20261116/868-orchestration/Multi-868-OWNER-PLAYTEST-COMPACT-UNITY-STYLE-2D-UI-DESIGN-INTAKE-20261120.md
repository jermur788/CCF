## 1. Actual owner feedback, not general suggestions

After personally using the browser 2D Stand Map, owner says:
1. **Do not make the game one enormous page.** It must be effectively **one useful desktop screen** with the map and planning controls visible, not a 100-row table and history section all the way down. Scrolling long distances to perform the core action is unacceptable.
2. **Follow the existing Unity Stand Map interface.** Significant UI and map-design work already went into the Unity version, including more visually developed forestry map drawing. Replicate its composition and visual language as closely as reasonably possible in the standalone 2D browser UI. **Inspect source and current authoritative Unity screenshots** rather than inventing a new visual identity; report any model/medium differences honestly.
3. **Compact directional and zoom widget.** Replace seven widely separated full-text map controls (`Pan north/south/east/west`, `Zoom in/out`, `Whole area`) with an intuitive spatial four-arrow D-pad and +/− (and fit/home) at the side/corner of the map, similar to ordinary mapping UIs. Reduce screen usage without making targets too small or unlabeled for keyboard/screen readers.
4. **Avoid repeated free-text felling reasons.** Typing a reason for each tree is frustrating. Owner proposed either (a) remove the feature entirely or (b) choose common reasons from a dropdown. **Manager recommendation, not yet owner decision:** a small selectable predefined reason taxonomy with **Other / custom reason** where necessary; record an actual reason with each order. Avoid deleting audit provenance or creating generic false ecological claims.

## 3. Recommended minimal coherent design (PROPOSAL — not implementation permission)

**Desktop e.g. 1280×720 or larger:** one viewport, short status/header across top; **large map left** roughly 60–70% and **right-hand narrow planning panel** containing selected tree, reason picker, pending/approve/execute and year advance. Keep result toast/status visible without page jumping. In map corner place a **D-pad compass arrow cluster + − and fit**, spatially intuitive with accessible labels/tooltips, 44px minimum pointer targets as required by prior review. Use icon buttons with `aria-label="Pan north"` etc, functional keyboard controls/focus order. Technical SHA/provenance, all-tree table and lengthy history should remain **available in collapsible, tabbed or bounded independently scrolling secondary panels**, not permanently occupy main page height. **Do not drop keyboard/screen-reader exact-ID table path**. The main map should use Unity Stand Map visual cues where applicable to the *existing* 100 synthetic trees (differentiated canopy/legend, north, scale, measurement), while preserving exact positions/radii/status rings and real Fell→stump map outcome.

**At smaller widths, 200% zoom and mobile:** use proportionate reflow/panels rather than squeeze/clip. A one-viewport desktop target **does not mean forcing all sections into 720 CSS px at all sizes**; graceful stacked accessible scrolling at accessibility zoom is expected. This explicitly remedies the previous one-column-at-all-widths workaround without reintroducing its failures.

**Felling reasons:** favour dropdown with an **owner-approved small controlled list** plus `Other (type reason)`; candidate descriptions, NOT approved categorical forestry truth:
- Competing with a retained crop tree
- Poor form / stem quality
- Damaged or declining tree
- Create growing space / light
- Other — enter a reason

The exact reason text recorded with each tree's order must remain human-readable and visible in approval/execute/history. If the reason is changed after approval, the existing fence/replay protections must reject stale execution; no implicit default implying a management judgement. A repeated choice UI may retain a last-used reason for the current UI session **only if explicitly approved**, not behind-the-scenes auto-fell.

**Alternative owner option:** no reason requirement (would entail changed policy, core validation and provenance) — do not implement this without explicit approval.
