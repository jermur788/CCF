## 2. Crucial model distinction and anti-invention boundary

- `Tools/MultiRackSitkaP1Lab/src/Core/Domain.cs` explicitly states `DerivedP1ThirtyMetreExperimentV1` is a synthetic 30×30m adult Sitka experiment: **NOT Unity numerical/geometric parity and NOT an Irish field forecast**. Existing #874 UI is genuine relative to its own engine, but is NOT the Unity Scenario One engine rendered in 2D.
- `AnnualRules.cs` competition cutoff is 8 m with its own Hegyi distance floor and annual growth response. The Unity competitor list decomposes competition via `CropTreeCompetition.cs` and `ScenarioOne/CompetitionShare.cs`; similar motivation **does not establish bitwise/equation parity** or equal CI units. The full UI should label which model generated its reading; any unified numerical contract requires separate approved scientific decision, fixtures and risk-based qualification.
- No source-verified 2D light, seed-bearing or regeneration state exists in the inspected records. Inventing overlays/diagnoses in browser code, doing random seed rolls, or labelling a poor-form tree without a measured variable would mislead the player.
- The eventual project direction is a shared single forestry simulation engine under 2D/3D presentations, but this needs an explicit approved cross-system architecture/spec, not an implicit wholesale rewrite, broad Core write grant, shared save-policy decision or currently forbidden G1 multi-rack extrapolation.
- Owner's phrase **“everything that's in the 3D should be in the 2D”** is treated as the **feature parity product goal**. Not every 3D interaction must be literally translated: free camera walking, target reticle, movement, VR-like navigation and Unity Editor behaviours need *2D-equivalent player outcomes*, not unneeded copy of physical UI. Don't add features not grounded in 3D research/owner approval or accidentally remove legitimate safety guards #849 already offers.
