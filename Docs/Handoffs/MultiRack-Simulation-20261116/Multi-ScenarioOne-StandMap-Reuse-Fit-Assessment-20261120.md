# Multi — Scenario One five-rack Stand Map reuse assessment

**20 November 2026 | Multi 2D Manager | GitHub source and approved design review; no Unity screenshot/runtime test or source edits**

## Decision

**FIT FOR PURPOSE AS A SHARED MAP PRESENTATION FOUNDATION WITH ADAPTATION; NOT FIT AS AN UNMODIFIED PLAYER-SESSION OR FIVE-RACK GAMEPLAY COMPONENT.** Reuse the proven world-metre transform, source-derived view/data model pattern, C# canopy raster and draw-plan primitives, readable cartographic visual language, legend and visual-state distinctions. Keep simulation ownership in the authoritative Multi C# G2 continuation, not Scenario One's `ForestTree` scene scan and not the map. The Unity-specific canvases and layout may be used inside Unity, while a standalone 2D interface should call the same *presentation/read model* through a suitable frontend drawing adapter rather than embedding Unity UI Toolkit. This is an architectural direction for an upcoming spec/packet, not authorisation to edit the owned Scenario One files or assert a compiled shared library exists.

## Fit matrix

| Component/design | Decision | Why |
|---|---|---|
| World X/Z metres / north-up projection | **REUSE design and, subject to licence/ownership scope, pure C# implementation** | Same coordinates and authoritative positions can project in Unity and standalone 2D. |
| True-position/true-crown canopy, modelled death and cosmetic texture | **REUSE/ADAPT** | A clear forester's stand view; source values rather than decorative invented ecology. Scale-dependent rendering requires profiling. |
| Unity-free `StandMapModel`, draw-plan, transform, symbols | **ADAPT into a shared presentation layer only if exact dependencies can be isolated** | C# portability possible, but model contains Scenario One rack fields, has mutable lists and currently drops exact selectable TreeId. No speculative shared-engine rewrite. |
| Unity `StandMapSurface`/`Canvas`/`CanopyLayer` | **REUSE in Unity; do not copy into standalone as-is** | Depends on Unity UI Toolkit and Unity textures. Standalone needs its own paint/input host over a canonical view/draw contract. |
| `StandMapSource` live scan | **DO NOT REUSE as Multi source adapter** | Pulls `ForestTree` from Unity and `ScenarioOneManager`. Multi must read exact `AnnualContinuation` committed roster and token atomically; large forests must not depend on scanning all Unity GameObjects. |
| Five-rack geometry, five-entrance goal, spacing, editor/snapping, headland, path and orange field-marking | **DO NOT TRANSFER into current Multi one-area gameplay** | Original Scenario One Enlarged80-specific teaching and access system; no five racks in 30m Multi fixture. Never manufacture spatial coverage/equivalent rack identities. Keep these as a separately optional map capability for a future proven multi-area game. |
| Suggested/draft/confirmed/actual status styling and legend | **REUSE SEMANTICS, adapt labels** | Work Plan has pending/approved/executed distinction; a drawing is never proof of a real Fell. |
| Tree selection gesture and inspector | **ADAPT, NOT copy rack selection** | Need exact stable `TreeId`, alive/dead distinction, source token and plan-state revision. `MapTree` currently lacks `TreeId`; a guessed coordinate/seed/nearest-crown ID is unsafe, especially when crowns overlap. |
| Performance/stable rendering | **REUSE strategy, MEASURE** | Canopy and static layers change less than player pointer, sprite caching and incremental steps help small cases; 768/256 fixed pixels and per-tree stamps are not a proven 100k/1m rendering strategy. |
| Visual design | **ADOPT AS DEFAULT VISUAL REFERENCE, not certified pixel-identical** | Existing Scenario One visual spec says Stand Map is primary reference; actual Unity screenshot/reference image was not available for a direct visual comparison. Validate later with owner screenshots or qualified Unity capture. |

## Smallest implementation consequence

For the first genuine Multi playable slice, **do not rewrite Scenario One map or recompile its Unity-bound source into the standalone lab**. Use the accepted original G2+A1 `4bb80973` as authoritative simulation, then build a **small source-owned, lock-consistent immutable session projection** containing the exact WorkSourceToken, frame, each `TreeId`/X/Z/crown and live/mark status, and pending/approved/executed state. Connect a minimal 2D map using the **same X/Z and visual-state conventions**; if actual code reuse of the pure drawing/types is safe and approved after dependency inspection, reuse them instead of duplicating. Unity later consumes the same source-controlled tree and event identity through a dedicated projection/adaptor, while keeping its UI Toolkit renderer as a presentation. No secondary forest calculator, independent fake tree state, invented map-derived authoritative Fell or scope expansion.

Use the already approved Stage5 UX and adapter docs. Before code begins, perform **one bounded exact compile/dependency and file-ownership check** on the selected map types; list all reused/compile-linked Scenario One source paths expressly, with owner grant, no implied write access. The previously granted V-01 covers **only** `SitkaGrowthModel.cs` and `SimulationRandom.cs`; it does **not** authorise linking the Stand Map files as new shared source. If adapting map code in place would overlap Scenario One source ownership or require pulling Unity dependencies into the lab, prefer a small standalone renderer using the inspected design and do not claim code reuse; record the concrete incompatibility.

**First player proof:** show one 30×30m undivided property with a current authoritative 100-tree view; exact-click live `TreeId`; reason → pending → review/approve → atomic Fell event → same-year visual changed canopy → safe source token refresh → next-year actual survivor roster and growth. Show G1 **DISABLED/Manual/NotCovered**, economics unavailable; no 5 racks. Independently verify source ID/shape alignment, drawn vs clicked identity, stale/duplicate/approved all-live/consent/replay states, and visual difference sourced from true engine events; UI accessibility and layout separate. Existing C# G2 A1 fix is source-approved/Tier2 only, not integrated/fully playable.

**Status:** `ARCHITECTURE/DESIGN FIT: CONDITIONAL YES`; `DIRECT UNMODIFIED COMPONENT REUSE: NO`; `PERFORMANCE/RUNNING UNITY/2D DEMO: NOT VERIFIED`. This document makes no code or protected spec/main changes, issues no source grant, and does not supersede existing Scenario One gameplay.
