## 2. Manager's bounded design guidance to avoid invented owner decisions

These are instructions for an honest **DRAFT**, not policy adoption.

**N-1 / portability B:** A fingerprint chain is not the bits produced on another platform, so it cannot replay an earlier arithmetic-different segment from genesis. The cheap B may be described only as an **attempt to replay when fingerprint diagnostics differ but arithmetic remains bit-identical**; failure must refuse without disk/live mutation. Actual cross-platform continuation under differing arithmetic would require a separately specified **platform-boundary state checkpoint or another verified portability model**, new envelope/replay/hash/cap math, and owner approval. Keep that **deferred future option, NOT introduced into §9.3's current no-checkpoint proposal**. Do not use this edit to decide B over A or C.

**N-2 / conservative A:** No owner has accepted how strict the gating fingerprint should be. Separate (i) candidate bit-affecting identity (e.g. numerical runtime/libm implementation), (ii) data/fixture/provenance compatibility (e.g. trust-table digest, separately verified, not libm), and (iii) diagnostic fields (kernel/os release, CPU model/full flags, routine runtime version). Do not *assert* which fields actually change bits before cross-host comparison evidence. If the DRAFT retains the strict equality A as a working conservative default, state **explicitly** that harmless OS/runtime patch, CPU flag or trust-table changes can force refusal and may make routine upgrades incompatible even if arithmetic is identical. This is a **costly, unapproved draft choice**, not a software-safe fact. If offering a narrower candidate gate, require conservative fail-closed behaviour for unknown relevant fields and later owner acceptance. No implicit portability grant.

**N-3 / detached replay:** Give the load job an explicit live-session concurrency fence: snapshot a monotonically increasing generation (including history-only/rejected events), history tip/revision and active session identity at dispatch; the job derives a detached candidate; **activation must be atomic** with rechecking the generation and identity under one exclusive commit/activation gate. If a command, save-epoch, unload or second load changes the session in between, abort with `SessionChanged` (or a distinct named proposal) and leave current memory, accepted commands and save bytes untouched; no lost update. Specify overlapping load jobs cancellation/serialization. Add negative test: mutating command while load runs → abort/refuse, never overwrite; history-only command test, simultaneous loads, and no partial state/disk changes. This is proposed, not implemented.

**Numeric cap constraints:** 64 MiB is **67,108,864 B** and 200,000 events has a threshold **335.54432 B/event** before subtracting header/snapshot. The #575 hypothetical 5,000-tree snapshot at 1,000,000 B plus a 2,048 B header yields **330.53408 B/event**. #578 reconstructed legal-looking 333 B and 321 B variants; 383 B is merely a counted example, **not a lower bound**. Never claim all 200,000 events unreachable until the canonical smallest **legal** envelope is specified, bytes counted from committed examples and the defined cap is reviewed. No unmeasured capacity, per-event hash cost or rate may be represented as supported performance.
