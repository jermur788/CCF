# Sen-1 + Multi #818 — T3 Fork orchestration-skill creator: cumulative usage, outcomes, limitations and requested improvements

**Author:** CCF Scenario One Overall Manager (#731), in collaboration with publicly recorded Multi Manager #730 outcomes. **Prepared 19 November 2026, ~15:36 UTC.** **Purpose:** substantive feedback to the creator/maintainer of the **T3 Fork (also called TG Fork in CCF packets) adaptive orchestration workflow/skill**. **This is a feedback handoff, not a request to modify CCF source, T3 skill code or live host permissions.** The developer/owner requested a retrospective on “all the different times” we have used orchestration so far, including positives, drawbacks and issues.

## Executive summary

**Keep the one-parent/multi-worker orchestration concept.** It is particularly effective when the work is substantial, decomposable into owned source/review/test roles and supports checkpoints. It produced independently checked technical and documentary results, recovered work after account exhaustion, made unqualified or unauthorised progress visible, and in one concrete clean-up run reclaimed ~7.44 GB without altering the live Unity lock. It can be dramatically more productive than many serial chats.

**But the skill/process needs stronger guardrails and less ceremony.** The repeated problems are: (1) a **delegated worker may retain ambient host filesystem/network/GitHub authority** despite a narrower verbal task; (2) an orchestrator can be told to implement a feature when the canonical spec, physical reservation or file custody still forbids production edits; (3) “completed” and green tests can overstate actual integration, runtime or user acceptance; (4) quota/session disruptions and immutable sign-off/cross-provider review create expensive restarts; (5) tool defaults put working state/logs on prohibited OS-root storage; and (6) excessive handoffs/reviews and branch proliferation waste attention for small, low-risk fixes.

**Most actionable request:** preflight should automatically report **what the parent and each child can actually read/write/execute**, physical owner and expiry, allowed file paths, nonroot storage, expected result and verification level; block dangerous action if the runtime's actual permissions do not match the plan. Make review/testing proportionate, one parent orchestration run default, and never infer success beyond evidence.

**Evidence caveat:** This is a **best-effort inventory of accessible, named CCF orchestrations**, not a claim to see every T3 session or to inspect the skill's private source/version. GitHub task packets/issues/results establish **native T3/OpenCode or TG Fork usage when explicitly recorded**; not every GitHub-only management packet proves that the T3 Fork *skill* was loaded/invoked. The 30 October historical ledger was **actually inspected from a user-supplied archive**, not from the GitHub repository (the ledger path at its pinned continuation ref returned 404). ## B. Observed advantages — retain

1. **One launch covers a full work package.** The owner can hand the parent a single durable packet, and the parent can allocate source, verification, review and integration support in the same session. This has worked for #780, #782, #802, #809, #811 and #814. It is less user-interruptive than a sequence of separately launched review chats.
2. **Specialised routing raises quality.** DeepSeek is effective as coordinator and bounded reviewer, Sol as source/algorithmic author, Claude for independent QA/visual/code inspection. #802's nonauthor review prevented deletion of still-owned evidence, and #789's mutant review found false confidence in a first PASS.
3. **Checkpoint and resume can salvage interrupted work.** #91 recorded OpenAI B quota exhaustion and DeepSeek completion of the already-published #151 work; #789 documented a same-model account switch without hiding it. This only works when branch, current artifacts and incomplete tests are captured before exhaustion.
4. **Parallel, disjoint lanes are genuinely useful.** Source + research + verification can proceed independently when they have different ownership and no physically shared Unity/Blender work; #773/#780 are examples. Exact branch/HEAD/result paths aid reproducibility.
5. **Safety gating is an actual strength when respected.** #776/#779 stopped unconfined Multi source; #777/#794/#802 correctly stopped when source/lease was missing, and #802's manifest/reviewer guarded destructive cleanup. A task can be valuable when **PARTIAL** and blocked, not only when green.
6. **Proportionate test levels accelerate usable results.** #809 M1/M2/M3 got the owner into the forest; #810 minimal restore tests and #814 bounded local checks were appropriate. More checks should be required at release/integration, not automatically at every source draft.
7. **Evidence-backed handoffs preserve context.** GitHub issue claims, exact candidate commits, actor/model/provider, per-file diffs, hash receipts and “NOT RUN” entries survive chat/session changes. The 30 Oct ledger's observed/claimed/inferred distinction is worth making standard.

## C. Observed problems — priority and concrete proposed skill changes

### P0: unsafe authority and provenance (must fail closed)

**P0-1 Whole-agent capabilities, not just a child shell command.** #776 and #779 show a tool-level/optional `bwrap` sandbox cannot confine a T3 delegate with ambient host filesystem, alternate edit tools, GitHub push-capable credentials, symlinks or unrestricted network. Require host-issued **actual permission envelopes** for the *entire* agent process/tools/connectors, not prompt-only claims or optional child commands. Preflight includes symlink/hardlink, wrong mount, alternate tools, Git worktree removal, open FDs and network/abstract sockets. If platform cannot enforce, report **UNCONFINED — NOT ELIGIBLE** for protected source, and do not silently fall back to “trusted”. No suggestion to run security evasion operations against live work.

**P0-2 Two distinct permissions:** (a) owner/product scope and approved spec; (b) operational writer/file/physical lease. #777/#794/#802 and #815 show these diverge. A parent can start G0 read-only while G1 source or G2 Unity is held; **neither source nor Editor runs** until a genuine current actor, exact branch/worktree and allowed-file ceiling + machine lock are observed and signed. The orchestrator itself cannot grant this to its own child by declaring it. This should be a built-in structured **admission state machine** with honest partial completion, not 20 paragraphs that can be misread. Manager-only spec acceptance should not be replaced by self-authored “orchestrator-approved subset”.

**P0-3 Physical lock safety.** A command named `status` may write; #794 proved nondeployed Ops copy can operate on live shared Unity lock, and #802 left 38 still capable. A worker's permission to “inspect” must not trigger mutating tool execution. Require **static/read-only admission checks**, mounted-device identity and process/lease readback; do not treat copied script bytes or GitHub claim as live custody. No arbitrary expiry, no forced release as a preflight repair.

**P0-4 Artifact attestation and per-output validator.** #813 passed scene smoke yet committed **invalid placement JSON**; #789's shallow bundle failed cloning; #785 FBX bytes differed across builds; #781's shortened registry lost owner rows. Teach the parent to **validate every produced file in its native format before the final PASS**: JSON parse/schema, archive clone/restore, deterministic asset manifest, Git coordination exact preservation invariants, signed save old-hash. The validation checklist should be built from **all changed paths and their consumers**, not just test names selected by the worker. A passing test on a *mirror* proves only mirror outputs (#789 V-02) until per-file provenance is reconciled.

### P1: resource, task coordination and review efficiency

**P1-1 Default storage placement:** physical `realpath` + `findmnt` and free-space check for worktree **and** harness caches, logs, `HOME`, `TMPDIR`, Blender/Unity import, archive and review output. T3 default root-backed worktrees/logs are problematic under this project's no-root policy (#781/#794); an exception granted for #785 cannot silently transfer. The parent needs usable non-root per-session `XDG` and temp configuration and must identify unavoidable system writes. Never relocate/copy secrets merely to pass a storage check.

**P1-2 Real provider availability and context-pressure telemetry:** surface per subscription account/pool quota remaining, reset window, authentication condition, active jobs and confidence; make **UNKNOWN** explicit, not guessed. Before sending a >large task to a 13%-remaining five-hour subscription (#91), estimate **capacity to completion**, checkpoint/stop margin and switching cost. Preserve source patch, test inventory, failure state and next command on account change, with no credential bypass. Record input/output tokens, calls, actual latency, retries, context compactions when available; resource/energy guesses must not be presented as measured.

**P1-3 Minimise review ceremony but keep risk-based independence.** The owner explicitly objected to too many reviews. #794 queued a QC review before #793 candidate existed; #814 ended with a formal “NEEDS CHANGES” over review wording after verified small fixes. Require **candidate-exists gate** before booking a reviewer. Prefer one distinct nonauthor review **inside the parent** with a changed-lines recheck in the same reviewer thread, and allow **Manager mechanical readback** for truly low-risk docs-only edits (as #793 did) without implying mandatory security/source review is waived. A reviewer must not self-approve their source. Save, signed persistence, destructive cleanup, security and live Unity still merit high assurance.

**P1-4 Worktree and lock lifecycle garbage collection.** #781 left four retained worktrees at ~4.8 GB, #794 created several more. #802 removed seven verified and eighteen dirs but found ~200 old registered worktrees. Add a manifest at creation: owner, purpose, live lock, storage bytes, remote push, cleanup eligibility, retention horizon and evidence hash. On handoff offer **reviewed exact worktree retirement**, never glob deletion or automatic purge of unknown/dirty/owned data. Implement a compact retention dashboard and avoid redundant historical full-repo mirrors.

**P1-5 Per-role write/qualified status separation.** Use invariant status vocabulary `PREPARED → ADMITTED → IMPLEMENTED → REVIEWED → INTEGRATED → UNITY VERIFIED → OWNER ACCEPTED`, with independent `BLOCKED / PARTIAL / NOT RUN` for every required gate. #777 docs complete is not a loop; #782 document quality is not spec approval; #802 cleanup is not lock containment; #809 scene smoke is not owner acceptance; #815 source compile is not Unity Play; #789 scratch Q is not main integration. Tool-generated status should cite actual candidate and result source. Don't let issue title or green test badge overwrite explicit incompleteness.

**P1-6 Smart decomposition / fewer nested forks.** Choose one substantial parent for genuine multiphase implementation, cap child count by ownership/parallelizable work, and do not spin up another reviewer or whole new packet for a missing comma/one paragraph. If a new worker lacks a current branch, exact test/state/API scope and physical slot, do G0 only and publish one blocker decision, not an escalating chain of documents.

### P2: UX, learning and evidence design

**P2-1 Operator view should show five facts, at a glance:** **who owns each path**, **what is runnable now**, **which gates passed/failed**, **what was actually changed**, **what is next / what user must do**. Distinguish “source compiled” from “Unity Editor imported”, “unit test” from “real Play” and “ready for owner's walk” from “owner accepted”. One concise running table and one final result should be more prominent than nested handoff verbosity.

**P2-2 Make routing learning evidence-first, not anecdotal.** Adopt the inspected candidate `ORCHESTRATION-EVIDENCE-APPENDIX-V2.md` categories: observed fact, orchestrator claim, retrospective inference; capacity fit/uncertainty, context pressure, provider reasoning/role, test/acceptance result, retries, rework, failure class and resource proxies. **Do not** treat it as installed policy or claim 30 Oct historical data reflects current model cost. Suggested experiment: compare equal-scope single-worker vs DeepSeek-parent+two-child, preserving actual granted lane, measuring completion at the same acceptance gate, wall time, model calls/tokens, review defects, failed/blocked starts, storage churn and owner interventions. No unsupported “faster/cheaper by X%” without data.

**P2-3 Cross-chat delivery.** Automatically emit a paste-ready **single launch message + stable GitHub handoff URL** for a new orchestrator; for a manager-to-manager transfer, also include exact accountable owner, branch/worktree/claim, required user action and whether dashboard/Drive mirror was verified. Do not assume another chat can see the original chat or project attachment. Never send task dispatch to a model/account that is merely listed, unauthenticated or capacity UNKNOWN as though already RUNNING.

## D. Proposed acceptance tests for the T3 Fork skill maintainer

1. **Unauthorized edit negative:** a delegated worker explicitly confined to A must fail to edit B using *every* supported tool, including alternate Git write paths, symlink traversal, shell and connector; reviewer captures the exact denied operation. An optional `bwrap` wrapper applied only to a tool subprocess is insufficient.
2. **Missing lease:** a parent with read-only Git but no physical source/Unity reservation may publish G0 and **cannot** mark source code or Editor PASS; no force/status side effects.
3. **Low quota / account drop:** actor at marginal five-hour capacity checkpoints cleanly; rerouted actor resumes from verified branch and state without pretending the original author completed it.
4. **Subtle artifact failure:** changed scene plus malformed JSON must cause overall artifact validation FAIL even if Unity movement smoke passes; a shallow bundle must fail a real clone/restore test.
5. **Conflicted specs:** a DRAFT Compact feature and unresolved owner M-A threshold should run pre-approved primitives but refuse to implement new completion/storage semantics.
6. **No unnecessary review:** one punctuation-only, schema-checked fix gets direct author validation; high-risk save/deletion keeps a distinct nonauthor review; reviewer does not start before candidate exists.
7. **No-root placement:** orchestrator actually probes its worktrees, scratch, cache, tool logs and Unity/Blender temp; fails if root writes exceed policy without a scoped owner exception.
8. **Truthful final status:** report separately a valid offline feature, a blocked Unity feature, a partially deleted unsafe legacy fleet and a verified transferred archive; never collapse to “DONE”.
