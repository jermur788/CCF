## 3. Alternative evaluation and recommendation

**E — Establish full existing central route + northern continuation at new Enlarged80 start.** Recommend as the first product candidate: avoids inventing a new route construction minigame and supports a coherent lesson where player plans **five branching racks** from an already present feeder. The existing track must be a real, accessible starting condition, with coherent new-world tree exclusion, `Track`/`Headland`/`Site` masks and views. Construction cost is historical/sunk; **no free new work order**, new Fell marks or automatic tree clearance. Old saves retain their historical starting world without retroactive north extension. A version-aware start-state rule must be specified rather than trusting the pre-existing southern approach's occupancy heuristic.

**P — Existing central route + player-proposed northern extension.** Higher implementation and teaching cost. Extension is ghost-only until a separate, accepted route-work order, cost, tree/terrain treatment, Work Plan approval and execution pipeline exists. Do not create an approved button that pretends the corridor is cleared, or auto-apply track masks to an unexecuted proposal. Not recommended for first slice absent a specific user desire to play route construction.

**F — Constrained present Rack V2/headland baseline.** Safest fallback if E cannot be reconciled with tree/turning/coverage/save policy. Preserves parallel-derived MFM and existing confirmations, but **does not deliver** the connected herringbone preference. Label it an explicit fallback, not a hidden success.

**No production selection was made.** Q1 user/Manager must approve E vs P/F on substantive evidence; the D-070 workbench retirement goal is already confirmed, but its safe implementation is a different claim.

## 4. Proposed but unapproved cross-system contract

- **Five actual branches, feeder separate.** 45° off north / 3+2 is a **reference search target**, not a qualified or mandatory exact set. Keep 16–20 m stand-specific advice distinct from hard validity. Each rack needs real connected spine/headland entrance, reachable first-removal trunk, valid width/length/corridor clearance, turn and tree interaction. Maintain current failure reasons until an approved revalidation changes them.
- **One rack identity, one owner.** Keep existing confirmed rack plan and Work Plan ordering; never build a second map/world rack system. A new deterministic **two-family** MFM method may be additive only when legacy `Derive` legitimately refuses a narrowly eligible plan. Existing valid legacy plans must continue on legacy unchanged; invalid/four-plus-one/third-family/chaining cases do not silently pass.
- **Finite access and unique treatment.** No two strips claim the same cell/stem/area; use deterministic tie rules and conservative Manual/NotCovered for far/ambiguous locations. Current 9 m teaching half-width is **not** an access/reach cap. The cross-family one-sample hypothesis needs overlap-free sample and independently supported comparability, not just a geometric algorithm.
- **Validate all transitions.** Invalid/disconnected sketches can stay *proposed* with explanations; Confirm and any authoritative confirmed edit must fail closed against geometry/selected MFM derivation, or reopen and reconfirm. A previously confirmed-invalid saved plan must load conservatively with new unsafe MFM/work paused, but completed work/history intact. Stable rack IDs alone do not prove stable unit meaning or hash/save compatibility.
- **One projection vocabulary:** **Existing** infrastructure, **Proposed** ghost, **Confirmed** geometry/pending work, physically orange **Marked** entrance, Work Plan **Approved** orders, **Executed** changes to authoritative tree/terrain/work state. All three views and Objective 1/work guidance show truthful distinctions; #258/#282 educational diagram does not create infrastructure.
- **Workbench:** D-070 calls for retiring only the unused workbench's future starting-world placement and MFM Site/starting-tree footprint, preserving reusable code/assets. Test old IDs and dependencies; do not auto-delete every other hidden buildable. **#284 is separate, gated local T3 work**, not implied by this browser result.
