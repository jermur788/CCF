## Verdict: **NEEDS CHANGES** — 4 blocking findings, 7 non-blocking notes

The product scope is faithful to D-072/D-071 and the central source discrepancy is correctly diagnosed. ## Blocking findings

### B1 — The spec does not forbid the obvious (wrong) mechanism: appending the headland to `model.Paths`
Spec: `spec.md:30` (FR-M3 "dedicated display-only, full-map-only geometry layer **or equivalent**"), `plan.md:10` ("prefer existing model/draw vocabulary with explicit visibility guard"), packet `:20`.

Evidence that the natural route fails:
- `StandMapDrawPlan.cs:116-130` draws **every** `model.Paths` entry, guarded only by `StandMapSymbols.IsDrawn(MapSymbol.Path, detail)`. `StandMapSymbols.cs:77` registers `Path` with `inMini: true`, and `IsDrawn` (`:119`) is per-symbol, so a symbol-level guard cannot make one path full-only. `MapPath` (`StandMapModel.cs:77-81`) has no `FullOnly` flag (only `MapRack` does, `:92`, honoured at `StandMapDrawPlan.cs:106,136`).
- Shared consumers of `model.Paths`: `StandMapDrawPlan.cs:117-119`, `StandMapLegend.cs:72`, `StandMapModel.cs:206-210` (static hash), and existing gates that assert exact counts/indices: `Tools/Verification/ScenarioOneNonUi/UnityGates/StandApproachVerification.cs:141,142,145,157,162,184,187,194` (`Paths.Count == 2` Enlarged80 / `== 1` Legacy40 and old world; `Paths[1]` is the approach extension) and `Tools/Verification/StandMap/StandMapParity.cs:227,231` (`Paths[0]`). In a fresh V2 world that Enlarged80 case is V2-active, so appending would flip `2` to `3` and break a currently-passing gate, tempting a "fix the test" edit that weakens it.
- Minimap consumers of the same model: `HudMinimapView.cs:84-86` (`surface.Sync(model)` with `MapDetail.Mini`) **and** the overview surface inside the Stand Map screen, `StandMapView.cs:173` (`new StandMapSurface(MapDetail.Mini)`), fed `ui.MapSource.Model` at `:219-221`. Both go through `StandMapDrawPlan.BuildStatic`, so one `full` guard in the draw plan covers both; nothing else in `UI/` reads `Paths` (grep of `Assets` and `Tools`).

**Required spec change** (replace the "or equivalent" wording of FR-M3 with a binding mechanism): the headland/feeder is held in a **new, separate model collection** (e.g. `StandMapModel.HeadlandSurfaces`, plain numbers, no `UnityEngine`), never in `model.Paths`; `model.Paths` content, count and order stay byte-identical in every state (so the cited gates stay valid unmodified); `StandMapDrawPlan.BuildStatic` draws the new collection only under `full` (explicit `detail == MapDetail.Full`, not a symbol `InMini` flag); the new collection is mixed into `StaticContentHash` (otherwise the layer is not repainted and the static-version key at `StandMapView.cs:226-229` does not change); `StandMapLegend` gets its own gated entry (see N3). Add a required offline test: `BuildStatic(model, side, MapDetail.Mini)` item list is element-for-element identical with and without the new collection populated.

### B2 — Applicability gate and invalidation are under-specified, and the template/surface proof is impossible under the spec's own file-freeze
Spec: `spec.md:26` (FR-M1), `:32` (FR-M4), `:34` (FR-M5 forbids touching `ScenarioOneHeadlandPresentation.cs`), packet `:22`.

Evidence:
- The only runtime truth for "headland exists in 3D" is `ScenarioOneHeadlandPresentation.Reconcile` (`:53-60`): `scenario.RackPlanningV2Active` **and** `CreateSurface()` having succeeded, which requires an object named `"Dirt Path 00"` with a `Renderer` (`:64-66`; returns `null` otherwise and retries every `LateUpdate`, `:51,:56-57`). The surface field is `private` (`:43`), so source outside that file cannot read "template present" without either a new accessor (forbidden by FR-M5) or a name/hierarchy lookup.
- `RackPlanningV2Active` itself is a reliable, already-documented single answer: `ScenarioOneManager.RackPlan.cs:30-40` (model == V2 **and** `StandGeometryModelVersion == Enlarged80`; the comment explicitly says Legacy40, Reference Future v1, pre-v21 saves and pre-V2 Enlarged80 continuations are *not* V2). Source reads it already at `StandMapSource.cs:264`. So the four named negative cases are genuinely distinguishable by that flag; only "template/surface present" is not.
- **Cache hazard:** `ReadScenery` (`:342`) is cached on `sceneryKey = StandGeometryModelVersion*1_000_000 + StandApproachPath.Version` (`:147-152`). `rackPlanningModel` is not in that key. A load from a non-V2 Enlarged80 save to a V2 save (or vice versa) keeps the geometry model and may not bump `StandApproachPath.Version`, so a headland computed in `ReadScenery` would be **stale/phantom** or **missing**. The racks are the opposite: re-read every 0.25 s (`:163-169`) and `v2` is recomputed there (`:264`).
- FR-M4's "STOP with evidence" is an implementer-time stop; the spec never states the **runtime default** when proof is unavailable, which is where phantom infrastructure would appear.

**Required spec change:** (a) the gate is a single pure predicate over named inputs — `rackPlanningV2Active` (read from `ScenarioOneManager.RackPlanningV2Active`, not re-derived) **and** surface-present — and is evaluated on the existing 0.25 s rack-read cadence or added to the scenery key; it must not hang off the geometry-only `sceneryKey`. (b) Name the permitted read-only proof of "surface present": cache the `ScenarioOneHeadlandPresentation` reference (it is added at `ForestStartingStand.cs:54-55`) and test its child `"Scenario One V2 Headland"` `activeSelf`/null; retry only while V2 is active and the reference is unresolved, never a per-frame `GameObject.Find`/`FindObjects`; **or** explicitly grant Manager-approved read-only accessor on the presentation (one `public bool SurfaceActive`), as a single named exception to FR-M5. (c) State the runtime default: **any gate input missing/unresolved ⇒ draw nothing** (never "assume present because V2"). (d) State that the "headland ends on the approach" part additionally requires the approach to exist; see N5.

### B3 — Junction/width/pad rendering rule is a prohibition without a mechanism (false duplication and width exaggeration are the likely outcome)
Spec: `spec.md:28` (FR-M2 "no duplicate overlay bands at the junction … that exaggerate actual width", "pads where supported").

Evidence (computed, not assumed): `ScenarioOneHeadlandGeometry.PathX = -2.436166` is exactly the x of the **existing approach track** at the feeder's z. I replicated `StandApproachRoute.Build` (`StepM 0.5`, `BendLengthM 7`, smoothstep bend) from the scene's `Dirt Path 00` pose (`ForestTest.unity`: x −0.9285, z −14.75, yaw 27.17°) and the route reaches **x = −2.43617 at z ≈ −27.49** (`StandApproachPath.cs:47-70`). Those planks are named `"Dirt Path X000…"` (`StandApproachPath.cs:27,63`) so they are already in `model.Paths[1]` via the `"Dirt Path"` prefix (`StandMapSource.cs:45,349`). Therefore the feeder **terminates on the centre line of an already-drawn band**, and `StandMapDrawPlan.cs:121-129` draws each path as casing then tan *per path*. If the headland is drawn after `Paths` with its own dark casing, its casing crosses the approach tan band (a visible dark bar at the junction); if drawn before, its tan is overpainted but the 4.4 m pads (`PadRadius 2.2`, `Geometry.cs:13`; mesh `Presentation.cs:79-80`) are wider than the 2.6 m track and read as "exaggerated width". The 3D mesh also has 1.3 m round ends (`:76-77`); the canvas draws solid lines with round caps (`StandMapCanvas.cs:79`), so lines match the ends, but pads are not lines.

**Required spec change:** state the draw rule — all headland casings are drawn **before** any tan band of either layer (or the headland layer is drawn entirely beneath `Paths` with the same casing/tan styles) so the junction reads as a union, not a crossing; segments are exactly the three source segments (west strip `(−35.4,−37.7)→(−35.4,37.7)`; feeder `(−35.4,−27.4)→(−2.436166,−27.4)`; width `Width` = 2.6 m = the plank width); the feeder stops at `PathX` and is not extended; no segment other than these three; and decide pads explicitly: **either** omit pads (state "pads are not drawn; junction discs are a 3D mesh detail") **or** draw them as filled discs of `PadRadius` at exactly the two source points, with the same fill/casing. Replace "pads where supported" with that decision. Add an offline draw-plan test that counts items and asserts no item outside those segments/discs.

### B4 — The required "source-only" tests cannot be written honestly with the spec as it stands (no pure seam, constants not reachable offline, cache test unmeasurable)
Spec: `spec.md:19` ("use the C# constants directly"), packet `:24`, `tasks.md:18`.

Evidence: the offline map harness compiles the *production* map files because they contain no `UnityEngine` (`Tools/Verification/StandMap/OfflineLogic/StandMapOfflineCheck.cs:4-5`). `ScenarioOneHeadlandGeometry.cs` imports `UnityEngine` and uses `Vector3`/`Mathf` (`:1,:16,:30`), so a plain-.NET draw plan or model cannot reference it. The repo already solved this once by reading the constants from the source **text** (`Tools/Verification/MfmCoverageWorld/OfflineLogic/CoverageWorldOfflineCheck.cs:91-101`, regex `const float NAME = …f;`). Likewise "cached invalidation, no new scene scanning" has no observable without a counter; the existing precedent is `TreeScans`/`CanopyChanges` (`StandMapSource.cs:55-57`).

**Required spec change:** (a) the geometry→model projection happens in `StandMapSource` (Unity side, reading `ScenarioOneHeadlandGeometry` constants — satisfying the "no copied array" rule), and produces plain model data; the draw plan and model stay free of `UnityEngine`. (b) The applicability gate is a **pure static function** (inputs: V2 flag, geometry model/Enlarged80, surface-present) callable from the offline harness, with tests for exactly: V2+Enlarged80+present ⇒ show; Legacy40; Reference Future v1 preview; non-V2 Enlarged80; V2 with surface absent ⇒ hide. (c) An offline constants-parity check (regex against `ScenarioOneHeadlandGeometry.cs`, as the coverage check does) asserting the model endpoints/width equal the constants. (d) A read counter on the headland computation (like `TreeScans`) so a verification can show a walk and map refresh do not recompute it. (e) Name the checks that remain **NOT RUN until Unity**: actual gate evaluation against the live presentation, pixels, minimap/overview panels as rendered, and the existing `StandApproachVerification`/`StandMapParity` gates still passing.

## Answers to the ten review questions

1. **Option B fidelity — faithful.** `spec.md:10` is exactly "repair the map presentation of the existing headland/feeder, then a faithful five-parallel-rack diagram"; D-072 (`decision-log.md` row D-072) and D-071 agree; no new physical geometry, racks, saves, northern spine, herringbone or MFM change is introduced (`spec.md:34,48`). No concealed gameplay change found. One nuance: `spec.md:12` says T2 "cues remain valid unless explicitly tightened here" and `spec.md:32` demands that the map not disturb "edit overlays"; both are compatible. Creep risk only via B1/B2/B3 (implementer improvising the mechanism).
2. **Discrepancy — accurate, with refinements.** Confirmed: `ReadScenery` collects only `"Dirt Path"` transforms (`StandMapSource.cs:342-368`, the spec's `342–377` range is right); `ScenarioOneHeadlandPresentation` builds one mesh object named `"Scenario One V2 Headland"` (`:82-91`) not matching the prefix; `StandMapDrawPlan` draws only `model.Paths` as paths (`:116-130`). Additional facts that change the analysis: (i) the feeder's far end lies on the approach planks that **are** in `model.Paths[1]` (B3); (ii) the approach extension exists only in Enlarged80 worlds made with it (`StandApproachPath.cs:35-46`), see N5; (iii) the full Stand Map screen embeds a **Mini** overview (`StandMapView.cs:173`), which also reads the model (B1). No third representation of the headland exists on the map (grep: no map/UI reader of `ScenarioOneHeadlandGeometry`; its consumers are rack editing, MFM coverage, suggested layout and starting-stand tree clearance).
3. **Full-map-only — achievable cheaply, but the spec must pin the mechanism.** A separate model collection plus a `detail == Full` check in `BuildStatic` is a few lines and precedent exists (`MapRack.FullOnly`, `StandMapDrawPlan.cs:106,136`). Every consumer: `HudMinimapView.cs:84-86` (Mini), `StandMapView.cs:173/219-221` (Mini overview), `StandMapView.cs:124/219` full surface, `StandMapLegend.cs:72`. `StandMapCanopyRaster` and `StandMapTreatmentReview` do not read `Paths`. Not a blocking *risk* to the product, but the spec is currently permissive about *how* (B1).
4. **Gating — reliable only with `RackPlanningV2Active`; template presence needs a defined mechanism.** `RackPlan.cs:30-40` makes Legacy40 / Reference Future v1 / pre-V2 Enlarged80 / pre-v21 saves distinguishable (the manager is the single answer and the presentation uses the same flag at `:21`). Template/surface presence is not exposed and the spec forbids editing the presentation (B2). The spec does say STOP, but not "draw nothing at runtime when unproven".
5. **Geometry fidelity — constants and orientation correct.** `HeadlandX −35.4`, `SouthZ −37.7`, `NorthZ 37.7`, `FeederZ −27.4`, `PathX −2.436166`, `Width 2.6`, `PadRadius 2.2` (`Geometry.cs:7-13`); west strip is north–south (x fixed) and the feeder is a west–east segment at z −27.4 (`Presentation.cs:75-78`), so the spec's orientation statements (`spec.md:19,28`) are correct and there is no northern spine in the source. The spec text prohibits an extra northern spine and a horizontal south road but, for duplication/width, only prohibits (B3). The feeder lies between entrances 1 (z −35.27) and 2 (z −16.42) of the verified fixture, so it does not collide with a rack entrance.
6. **Determinism/performance — not yet well-specified** (B2, B4). FR-M4 is directionally right (no per-frame scene scan, no mesh reading, event/cache invalidation) but does not say *which* invalidation key or cadence. Also note that `ReadScenery` already performs a scene-wide `FindObjectsByType<Transform>` (`StandMapSource.cs:348`); the new layer must not add a second one, and must not be computed inside the 0.25 s read as a fresh scan. The existing per-LateUpdate `GameObject.Find("Dirt Path 00")` in the presentation (`:64`, only while the surface is missing) is pre-existing and out of scope.
7. **Negative compatibility — mostly protected by the file freeze, but not by tests.** Rack drawing/drag/Confirm, Work Plan, MFM and ecology are protected because the allowed files are map-only (`packet:20`, `spec.md:34`); the spec correctly forbids save fields. Gaps: B1 (existing count-asserting gates), the Mini overview inside the Stand Map, and the lack of a named "unchanged element-for-element" test for `model.Paths`, Mini draw plan and the five-rack `model.Racks` (packet `:24` asks for it but without the seam, B4). Old loaded saves are covered by the V2-flag gate (`ScenarioOneManager.cs:1491`: pre-v21 ⇒ Legacy).
8. **Diagram stage — coherent, with a provenance gap.** The fixture is consistent with the production recipe: `ScenarioOneSuggestedRackLayout.cs:22,28-57` uses `PO0203/PO1204/PO2003/PO2803/PO3803` and each tree's own Z; the blocked handoff's derived Zs (−35.27, −16.42, 0.24, 15.79, 35.23) give gaps 18.85/16.66/15.56/19.44 m (sum 70.50), matching the spec's `spec.md:20`. The Manager approval (`MANAGER-OBJECTIVE-GUIDANCE-SPEC-APPROVAL-20261106.md` Q2 row) does approve the recipe/criteria. Map→diagram ordering is enforceable by process only (Manager verdict + #200 ownership transfer), not by code; that is acceptable and stated three times (`spec.md:38,55`, `plan.md:12`, `tasks.md:11`). See N2 and N6.
9. **Testability — currently insufficient** (B4). With the four required changes the source-only suite can prove: model item count/endpoints/width equal constants; gate truth table; Mini draw plan unchanged; `model.Paths`/racks unchanged; no schema field added (diff review). Must remain runtime-only: live gate vs real presentation surface, rendering/pixels at 720p/1080p, minimap and overview as rendered, existing `StandApproachVerification`/`StandMapParity`/`StandMapOfflineCheck` still green, the historic feedback checker.

No missing *blocker* beyond B1–B4.

- **N4 (Mini overview wording).** State explicitly that the Mini overview embedded in the Stand Map screen (`StandMapView.cs:173`) also shows no headland ("full map only" means the `Full` surface).
