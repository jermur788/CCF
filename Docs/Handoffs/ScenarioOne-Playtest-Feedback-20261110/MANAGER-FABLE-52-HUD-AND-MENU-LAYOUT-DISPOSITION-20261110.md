## Latest user idea — numeric ecological indicator in top-right status strip (candidate, metric UNDECIDED)

The user wants a **small persistent top-right display** of **Year, current cash and useful general context**, and proposes **a number for biodiversity or something similar**. This is accepted as a UI design direction, not an acceptance of an invented biodiversity index.

Manager recommendation: reuse authoritative Year, cash and (if space) browsing status; consider **an ecological/habitat indicator** alongside them. A transparent numeric proxy may be a count of *established* tree species or a count of explicitly defined habitat features present, accompanied by a drill-down. A composite “Biodiversity 72/100” must **not** be shown as scientifically measured or accepted absent an approved definition, simulation coverage, calibration and product decision. The project models only a subset of biodiversity processes; deadwood, structural diversity, regeneration and tree species should be treated as distinct evidence/proxy categories, not assumed equivalent to whole biodiversity. Avoid rewarding one token planted tree as an automatically beneficial result.

Keep the strip compact at 720p and avoid duplicating a second bulky status panel. Always derive Year/cash/browse from current state; any habitat aggregate must specify denominators, threshold/eligibility and source, handle old worlds and snapshots conservatively, and state explicitly **GAMEPLAY INDICATOR, NOT EMPIRICAL BIODIVERSITY** if a numeric composite is chosen. Precise metric choice remains **OPEN, nonblocking** for card/keybar work. No ecology data or save fields are authorised by this preference.

## Latest direct player preference — Annual Review headings (binding design input)

The user explicitly rejects question-form Annual Review headings. Preserve **descriptive category headings**, such as **Work done**, **Money** and **Forest changes**, with a clear summary figure or sentence beneath each. Do not use headings such as “What did we do?”, “What did it cost?” or “What changed?” The earlier Manager suggestion of questions is withdrawn. This is a presentation requirement for any later Annual Review layout refinement; it does not authorise rewriting the current code or running Unity.

## Latest direct player preference — bottom HUD action buttons (binding design input)

The user additionally states: **“I also like having some of the useful buttons displayed at the bottom of the hud.”** The draft must **retain a bottom contextual action bar** rather than strip every control into a single word or hide all prompts. Use legible, button-like keycap affordances with short verb labels. Prioritise currently useful actions only: e.g., while inspecting a Crop Tree, **[1–5] Show neighbour / [V] More detail / [E] Close**; while walking, genuine current-stage **[M] Map / [O] Objectives / [Tab] Work Plan**, plus a valid context action. During rack planning and rack-spray stages, show the genuinely active prompts instead. Do **not** show [X] Fell or [C] Crop before those actions are enabled, or show fake clickable commands while the pointer is locked.

Where a real pointer/UI interaction mode permits it, these may be operable buttons using the same authoritative action handlers; when the player is in mouse-look/cursor-locked mode, they remain visible keyboard/controller prompts and must not claim mouse clickability. This is a **visible usability requirement**, subordinate to genuine input/state guards and avoiding new permanent shortcuts. Test legibility at 720p, keyboard-only use, reduced-motion, dynamic action changes and the one-bar footprint.

## Explicit corrections to the visual sketches

1. The Objective1 screenshots' [X] and [C] key hints must not appear when the real rack-first stage suppresses those actions. Show only keys the code actually allows; current TreeInspectionView already guards marking during RackFirstStageActive.
2. The image's highlighted Approve Work Plan control cannot pulse: it commits work. A static selected/default style may be used. Advance Year/Confirm Rack Plan and other destructive/commitment actions also never pulse under the prior ruling.
3. Back to forest is never disabled merely because the Annual Review has not been acknowledged; acknowledgement remains a separate explicit safe action.
4. 'Growth held back 54%' needs the technical qualifier 'of potential diameter growth' in visible text or immediate explanatory detail. An adjacent '13% share' label is a relative local-competition contribution. These percentages have different denominators.
5. The target tree card must not pretend qualitative health, ecological desirability or recommended felling is known from a competition index. Fable's example 'No single neighbour dominates' is a description of calculated shares only.
6. Sample values in the mock-ups and stitched forest backgrounds are illustrative, not current rendered state. Copy/source values must be bound to current authoritative data, not hard-coded.
