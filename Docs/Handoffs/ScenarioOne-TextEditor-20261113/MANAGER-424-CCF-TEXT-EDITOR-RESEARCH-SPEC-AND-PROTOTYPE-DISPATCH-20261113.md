## 1. What success looks like to the player/content owner

The user launches an ordinary browser-based editor locally, without the Unity Editor. It has a left sidebar of scenarios and ordered content sections; it opens each actual text page/step, shows all fields, lets the user change words, and proceeds **Previous / Next** in a consistent teaching order. It can search all imported text, reveal variants such as before/after approval, inspect original versus changed content, validate changes, and save/export the result in a **stable machine-readable content package** which a later approved Unity adapter can consume. The interface distinguishes **currently shipped in the inspected candidate**, **reviewed/approved copy not yet integrated**, and **draft/new scenarios**, and never pretends unknown future scenario text already exists.

The user must not have to browse C# source. Editing *visible wording* should not rename saved objective IDs, lesson progression keys, save data, tree/rack/work identities, calculations or dynamic placeholders. Editing an instruction changes the displayed sentence when subsequently integrated; it must not silently change the required action or completion predicate. An explanatory preview is useful, but a non-Unity preview must not be called pixel-perfect rendered Unity qualification.

**First valuable slice:** three-page introduction, Objectives topics/steps, teaching sequence, F1/first-use help, and key status/annual/result/Work Plan messages for the current true Scenario One. Broader coverage should be mapped and implemented until the audit identifies the *real* remaining categories, including conditional and generated strings. Build a visible **coverage report** (collected / conditional / generated / serialized / unlocated / explicitly out of scope), not an unsupported claim of "every text" from one code directory.
