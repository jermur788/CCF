## 2. Bottlenecks ranked by likely impact on the critical path

### A — Requirement/representation mismatch and late product choices (**very high delay contribution; evidence-backed**)

- The finished Rack V2 mechanics did not include the separate guided next-action UI/real-road Stand Map visuals the user expected (#281), even though earlier draft spec #258 described these. “rack updated” meant different delivered scopes to the team and the player.
- #296 first discovered late that **actual 3D headland/feeder geometry lives in a separate presentation mesh while the Stand Map reads only Dirt Path transforms**. The verified diagram could not simultaneously match actual geometry and the then-current Stand Map; worker correctly blocked without code. User first chose defer (option C), then later approved physically existing headland on map and diagram (D-072 Option B). #298 subsequently found four blocking spec defects before rerun. This is a product-representation and acceptance-design issue, not a C# inability to draw five racks. [Early DeepSeek Stage B handoff](https://github.com/jermur788/CCF/blob/docs/deepseek-orchestration-20261105-v1/Docs/Handoffs/ScenarioOne-Overnight-Playtest-Readiness-20261106/OVERNIGHT-EXECUTION-RESULT.md), [#298](https://github.com/jermur788/CCF/issues/298), [#294](https://github.com/jermur788/CCF/issues/294).
- **Avoidance:** before coding, have one short visual acceptance sheet showing **exact current screenshot**, intended Full Stand Map, Objective 1 card and five-rack diagram side by side; declare whether a drawn road already exists in 3D and which source is authoritative. Obtain one grouped product decision for all ambiguous layout/focus claims. The core interaction and the UX presentation must have separate completion labels.

### B — Verification tools repeatedly failed independent falsification (**very high and persistent; multiple review loops**)

- The source diagram/Map implementation became source-approved, but the **five-rack checker** went through #303 inventory reconciliation, #306 a directly authored orchestrator checker with no contemporaneous clean-start claim, #307 reviewer finding three critical integrity weaknesses (unprotected diagram bytes, weakened-checker false greens, overly broad stage allowlist), then #308 repair and #310 independent acceptance. Production checks were largely passing: the delay was dominated by proving the verifier could not silently accept altered source. [#306](https://github.com/jermur788/CCF/issues/306), [#307](https://github.com/jermur788/CCF/issues/307), [#308](https://github.com/jermur788/CCF/issues/308).
- The **Objective CTA Python lexical checker** had a larger spiral: #302 found source false greens; #304 repair; #305 uncovered **50 true false greens**; #309 repair; #314 found **26 additional** relevant false greens; repair loop fixed them; exact-head #314 rerun found **47 interpolation-hole** and **10 decoy pin-binding** false greens. The checker was attempting to prove broad C# UI behavior through expanding source-text/lexical rules; novel valid C# shapes kept defeating its assumptions. The reviewer scratch demonstrates two bounded guards are plausible, but does not prove a complete C# analysis. [#299](https://github.com/jermur788/CCF/issues/299), [#305](https://github.com/jermur788/CCF/issues/305), [#314](https://github.com/jermur788/CCF/issues/314), [#320](https://github.com/jermur788/CCF/issues/320).
- **Avoidance:** build a minimum trustworthy test oracle before feature coding. For static source checks, use AST/semantic analysis (Roslyn C#) for nontrivial C# class ownership/interpolation behavior where feasible, or strictly name lexical checker limitations and back it with a narrow set of real Unity end-to-end/negative tests. Keep the historical red and mutation tests; do not simply disable them to get green. Treat verifier-framework expansion as a separately planned tooling task rather than silently attaching unlimited scanner hardening to an apparently small UI change. Test the *test* with a small adversarial suite at inception, instead of discovering its trust model on the fifth review.

### C — Exact Unity environment, historic test debt and storage (**high safety/qualification cost; actual cold Editor time comparatively small**)

- The first #287 attempt could not acquire a Unity lease: the standalone clone was not registered and did not belong to the canonical Git store (#311/#312). The safe stop preserved work, but exposed late infrastructure readiness.
- On the eventual **64-minute** actual Unity lease, cold import was only **~10 minutes**. Bigger remaining problems: historical test pins still demanded **save version 23 while production was already version 24**; Workbench lifecycle assertion incorrectly assumed all prerequisite buildables had been constructed; saved-state versus true fresh scene lifecycle was conflated; runner could falsely return success without a terminal PASS and crash when the licence directory contained a nested directory; one of 1,344 trees was replaced after a supposed deterministic reset. These were mostly verification/provenance faults (tree cause still unproved), not established rack gameplay regressions. [#287](https://github.com/jermur788/CCF/issues/287), [#317](https://github.com/jermur788/CCF/issues/317).
- Unity rewrote **eight tracked files**, including Linux SDK/toolchain package **1.1.0→1.1.1** while the tracked candidate remained older, breaking exact package attribution and leaving the lane dirty. After the retained ~6.6 GiB cold Library, ZX20 had **21.62 GiB** free; a second ~6.8 GiB cold Library would cross the mandatory **15 GiB floor**, making integrated qualification unsafe. [#315 dossier](https://github.com/jermur788/CCF/blob/docs/mimo-scenario-one-overnight-20261107-v1/Docs/Handoffs/ScenarioOne-Overnight-Playtest-Readiness-20261107/FOCUSED-INTEGRATION-READINESS-DOSSIER.md).
- **Avoidance:** make a **preflight-only Unity readiness gate** (legitimate registered canonical-store worktree, real lock availability, clean tracked package version vs installed cache, free-space forecast, safe old-save fixtures) as soon as a Unity candidate is probable, without starting Editor early. Run a version/persistence harness health check **on the unchanged base** before attributing stale failures to a new feature. Plan one pinned head/one cold Library; have an explicit manager-approved strategy for Editor-owned rewritten files. Preserve lock and disk safety absolutely.

### D — Serial author/reviewer/Manager handoffs and human decision pauses (**substantial elapsed time; not all wasted**)

- The intended safety pattern required separate spec, author, independent reviewer, Manager verdict and new author after each adverse verdict. #294 explicitly paused at product/Manager gates more than once, including an initial decision to defer the diagram, later reversed to show the real roads. The 19.5-hour spec window includes one of those pauses and **is not 19.5 hours of writing**.
- This separation caught legitimate defects: drawing roads that were not on the actual Stand Map would mislead the user; unsafe Objective primaries and false-green checkers were real risks; a one-tree world substitution could invalidate frozen save/hash evidence. The bottleneck is not simply “too many tests”, but **late discovery plus approvals distributed across turns**.
- **Avoidance:** bundle questions into a single product decision before authoring; choose one frozen candidate and one independent adversarial review per well-bounded stage, with a finite defect-repair budget and an escalation route when the checker itself needs redesign. Advance independent research/source readiness in parallel only where no writer overlap; serialize Unity and shared file ownership. Do not force a Manager decision or weaken tests to hide a blocker.

### E — Provider availability and ancillary work (**real but smaller direct time cost**)

- Mimo's overnight #314 review hit **two OpenAI-family usage-limit failures around 03:52–04:02**, then used a different account/model in the same provider family as the author and disclosed weaker review independence. This cost about **10 minutes directly recorded** plus reviewer-routing constraints; not a reasonable explanation for 44 hours. [#313 entries 005–006](https://github.com/jermur788/CCF/blob/docs/mimo-scenario-one-overnight-20261107-v1/Docs/Handoffs/ScenarioOne-Overnight-Playtest-Readiness-20261107/MIMO-OVERNIGHT-EXECUTION-LEDGER.md).
- Other tasks during the window included the D-067 access-spine draft/research (#283/#285/#286/#288), D-071 context mirroring/attachments (#289/#292/#293), and ZX20 storage identity repair (#290). They consumed task slots and attention, but **GitHub does not establish that each sat on this rack-playtest critical path**. Do not add their issue lifetimes to the 44h claim or call them the root cause.
- **Avoidance:** reserve a capable genuinely independent reviewer at dispatch, preflight quotas before starting critical path, choose a fallback up front, and keep research/context publication off the urgent user-visible feature's execution queue unless it is a genuine dependency.

## 4. Measurement improvement: what we cannot currently answer

We cannot say accurately “35% of time was code review” or “12 hours were model rate limits”: evidence lacks a unified event clock and active-time/wait distinction. It would be misleading to add overlapping #295/#296/#299 or source/review issue lifetimes.

**For future task ledgers record these event transitions with ISO UTC timestamps and actual branch/commit:**
- **CREATED / READY**, **RUNNING_START**, **RUNNING_STOP**, **WAITING_MANAGER**, **WAITING_PRODUCT**, **WAITING_PROVIDER**, **BLOCKED_TOOLING**, **BLOCKED_TEST**, **UNITY_LEASE_ACQUIRED**, **UNITY_LEASE_RELEASED**, **HANDED_OFF**, **REVIEW_START**, **REVIEW_END**, **MANAGER_VERDICT**. Preserve each timestamp on every retry rather than overwriting.
- Fields: *single blocker cause code, owning model/provider/effort, source/test candidate, active session elapsed vs queue delay, real Unity runtime minutes, number of defects found by independent reviewer, repeated verifier false-greens, test mutation count, rejected/cancelled work, true source files changed, storage cost and safe recovery actions*.
- Report **critical path elapsed hours**, **sum of worker active hours**, **hours blocked on product/Manager**, **hours blocked by environment/capacity**, and **review loops** separately; never sum overlaps into wall-clock totals. Distinguish incident prevention from waste; independent review found substantive issues here.

**No product or implementation authority change is made by this retrospective.** The existing #318–#321 repair work and #322 Mimo run own their lanes/ledgers; this Manager report is separate and read-only against them. As of the audit, source repairs/reviews were underway; A–O integrated qualification remained NOT RUN. No Windows/Player build was authorised.

**Bottom line:** The largest avoidable multipliers appear to be (a) late mismatch between gameplay mechanics and the visible player expectation, (b) a home-grown source-checker becoming a larger programme than the UI change it checked, and (c) test/Unity environment debt discovered only at the final gate. Those are opportunities for earlier source/visual design and test-oracle qualification, not shortcuts around safety checks.
