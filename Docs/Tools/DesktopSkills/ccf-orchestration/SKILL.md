# CCF orchestration — skill for desktop ChatGPT / Codex

**Scope:** orchestration, dispatch, approvals, ownership, evidence and handoffs for `jermur788/CCF`. This skill is **not** authority to start coding, merge, run Unity, acquire a physical lease, edit a dirty worktree, or bypass a source gate. The owner's latest instruction and the **current** repository win over any statement in this skill.

## Before doing substantial CCF work

1. Identify actual task, assigned role (e.g., dedicated Multi 2D manager vs Scenario One manager), exact desired outcome, model/provider, execution host, available tools and any existing claim. **Do not infer that a role or lease transfers automatically.**
2. Inspect the current canonical repository documents, not stale local context: `AGENTS.md`; `Docs/Project/AgentWorkflow.md`; `Docs/Project/coordination/active-tasks.md` (live single-writer authority); `Docs/Project/decision-log.md`; `Docs/Project/current-milestone.md`; `Docs/Project/game-brief.md`; and any relevant accepted spec and GitHub handoff. Read the current `Docs/Project/unity-project-overview.md` when implementation facts matter. See [source map](references/source-map.md).
3. Inspect active GitHub issue and comments, current branch/HEAD, relevant commits and physical custody records **before** deciding whether a lock or approval is absent. If a document is inaccessible, declare the evidence gap. GitHub issue state alone never proves a local host/physical grant or clean Unity state.
4. Categorise evidence: directly inspected source/verified runtime, independent review, author-only result, gameplay calibration, forestry research, unverified assertion, or open decision.

## Decide and route

- For small bounded fixes, use **PACKET ONLY**. For new gameplay/player workflows, cross-system transactions, persistence, significant UX, forestry mechanics, multi-area source rules or costly ambiguity, use **SPEC REQUIRED**: `spec.md`, `plan.md`, `tasks.md`, `checklists/requirements.md`. Only the appropriate `APPROVED` or later spec state permits implementation; a `DRAFT` does not.
- Prioritise the **actual product outcome**, not a long sequence of documentation reviews. Use one proportionate independent review at material boundaries, combine related evidence discovery, and only escalate unresolved contradictions or risky source seams.
- Use GitHub/browser tools for read-only repository inspection and authorised documentation/issue changes. Use local Codex/Claude only if it has the **required real tool access** for source, builds, Unity, or physical verification. Do not pretend an unavailable tool, provider, skill, worktree, or desktop session exists.
- For Multi 2D, distinguish its **single undivided 30 m / 100-Sitka Stage 5 foundation** from the **near-term separate** sample-to-multiple-source-comparable-areas objective. Never invent a physical rack subsystem, comparator thresholds, source-field availability, or actual Fell. Require a proved G2 source-atomic once-only Fell and actual following-year ecology. Source evidence, technical approvals and live status must be refreshed at time of action.
- For Scenario One, follow its own latest accepted milestone/spec, ownership, saved-world and Unity gates; never import Multi assumptions or allow an unapproved Windows build.

## Lock, claim and physical safety

1. Check `active-tasks.md` and current issue thread before registering a new writer. One actual writable lane/worktree per owner; one primary writer per subsystem/file set. Stop on overlap; assign an interface or handoff instead of writing through a collision.
2. Before dispatching production work, link **every required spec approval**, GitHub file-writer authorisation and **actual current physical Ops reservation/lease**. A prospective reservation is not a granted lease. Do not run native source/Unity work if permissions or exact candidate verification are missing.
3. Create **one issue claim** per substantive dispatched task. Before the first write, register actual `[RUNNING]` with model/provider/session, branch/worktree, observed starting full HEAD, file allowlist, phase and permitted Ops scope. If unable to start, use `[BLOCKED]`. At completion publish a GitHub Markdown handoff, mark `[HANDED-OFF]`, and close. Claims track execution, but never override live single-writer authority.
4. Keep source, physical Unity machine-wide and desktop processes in their own permitted lanes. **Never** stash, clean, reset, discard, overwrite other agents' dirty files, kill competing processes, alter physical board/leases, bypass locks, rebaseline protected fixtures or weaken tests to obtain PASS without explicit authorisation.

## Handoff / acceptance sequence

- Each packet must give the **specific task outcome**, source spec/handoff links, difficulty/reason, best suited actual model, exclusive lane/branch/worktree/starting HEAD, claim/status, allowed edits and exclusions, expected positive and negative checks, required owner permissions, one exact durable Markdown result path, stop conditions and **one paste-ready dispatch line with a direct GitHub URL**.
- Workers hand back source evidence and a permanent GitHub Markdown result, not just a chat summary. The manager inspects the returned evidence and issues `APPROVED / NEEDS CHANGES / REJECTED` with the *scope* of that verdict (document quality, source review, feature qualification, integration). Distinguish **IMPLEMENTED, REVIEWED, INTEGRATED, VERIFIED and ACCEPTED**.
- Do not claim GitHub passing text or a local author test proves Unity import, native compile, source security, runtime/rendered behaviour or final integration. Re-test the exact candidate at proportionate Tier 1/Tier 2/Tier 3 levels under actual machine permissions.
- If the next step is clear, prepare one next executable handoff immediately. If a real approval, source evidence, ownership collision or product decision blocks progress, say exactly what is missing rather than dispatching speculative work.
- Git is canonical. Drive/dashboard are read-only mirrors; mark sync **NOT VERIFIED** until directly confirmed. Do not publish stale attachments as current.

## Response structure

Keep user-facing summaries concise and explicit: **what changed, what passed/failed, what it means, next action, user action required/none, and mirror status where applicable**. For an agent dispatch, link the exact verified permanent GitHub packet and include the copy/paste line. Avoid opaque commit hashes in user-facing prose (retain them in technical packets as needed).

It is an instruction-only skill, not an automation framework or a substitute for `AGENTS.md`.
