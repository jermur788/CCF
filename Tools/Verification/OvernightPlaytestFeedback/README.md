# Overnight playtest feedback — source baseline (#260)

Written against published player-test source commit `72b4efbd1c653fa2231f632a79030a83ff76f833`, independently of fixes #255/#256. Python 3 standard library, Git and a .NET SDK able to build `net8.0` are required; no packages are added. The SDK that actually runs is chosen by `dotnet` from the **current working directory** (`global.json`), not from the script's location or `TMPDIR`; the six SnapFar cases give identical output under SDK 8.0.133 and 10.0.114 (observed).

From this checkout's root:

```bash
python3 Tools/Verification/OvernightPlaytestFeedback/check_baseline.py
```

Every result is **SOURCE-STATIC**. The checker reads the current checkout, quotes exact C# literal fragments / expressions with file and line, and compares tracked production files against the recorded commit. It never changes source, existing tests, preferences, saves or Unity assets, and never launches Unity. Check 06b compiles/runs only `RackEditing.cs`, `RackGeometry.cs` and an embedded six-case driver with plain .NET, in an automatically removed OS temporary directory outside the repository. No Unity or Player build runs. The SOURCE-STATIC prefix describes the source/offline evidence tier; 06b executes isolated math rather than merely scanning text. It is independent of the working directory. Output has no timestamps or changing verification-branch HEAD, so identical source produces identical output.

Exit 1 means at least one feedback assertion is unmet, including the deliberately retained Objective 1 baseline failure; exit 0 means the selected source-policy and isolated-math assertions pass, not runtime qualification. NOT-TESTABLE observations never count as PASS. Exit 2 means missing source/anchor or another read/parse failure: inspect before interpreting any partial tally. An added/untracked production file is outside the tracked Git comparison; the C# inventory still reads it.

Checks cover the V2 Objective 1 concept's compact metre formatting, exact requested heading literal, source-material phrase, the Tree Marks legend's separate orange rack-removal and red Fell entries, Pro Silva mentions, rotation snap expressions, state-selected rack-edit instruction sentence, next-instruction path, primary CTA source and shared map/minimap source paths. The requested “duration” is actually rack spacing in metres. Both ASCII hyphen and the candidate's en dash are accepted; rejecting a space before m is a requested presentation format, not a functional defect, and is expected to flip with #255.

The phrase inventory scans ordinary/verbatim C# string tokens under `Assets/ForestPrototype/`, ignoring comments. It is deliberately conservative: a Pro Silva mention fails for human review rather than guessing whether it asserts a formal standard. It is not a full C# parser, evaluates no expressions/conditional compilation/interpolation, joins no dynamically composed text, and scans no serialized assets, localisation, external resources or binaries. The orange/Fell assertion is specifically the existing legend and separation sentence; it is not an exhaustive semantic language detector. Missing expected anchors fail with exit 2 rather than silently passing; checks 06a, 06c and 08 report a missing/unsupported policy expression, a missing/changed/ambiguous instruction sentence, or a missing/ambiguous/unsupported Objective CTA source shape as FAIL instead (exit 1, with a completed tally). Any later refactor needs deliberate checker review; do not relax it to hide a baseline failure.

**Nothing here proves visual layout, input behaviour or rendered correctness.** Exact heading presence alone cannot prove a heading is displayed. A shared map source cannot prove trail parity. Source `btn-primary` is not a measurement of user attention or keyboard focus. No forestry convention, Pro Silva standard, compile gate, simulation, persistence or platform qualification is established.

`baseline-output.txt` is the raw stdout of this bounded review-response run on the same pre-fix production baseline (exit 1): `PASS=6 FAIL=4 NOT-TESTABLE=2`, twelve tally rows (one new passing 06c; all previous results unchanged). The six 06b case diagnostics contribute one aggregate tally row. Two executions produced byte-identical output and no stderr. It is intentionally unchanged: re-running the current scanner on that original source still yields `6 PASS / 4 FAIL / 2 NOT-TESTABLE`, exit 1, but the test-08 diagnostic line now reads as a structural-contract failure (unnamed static `btn-primary` header button) with the same three source rows, so a regenerated file differs from this one only in that line. The original nine-row evidence is retained in Git at `62f1c1645b63f72125def83838e20847ece04e52`. Later production-state runs should be saved separately inside an owned evidence path. Manual Unity steps and the full limitations are in `Docs/Handoffs/Overnight-Continuation-20261104/BASELINE-VERIFICATION-HANDOFF.md`.

Check 08 checks a bounded, **conditional** CTA source contract (it replaced the original static "exactly one `btn-primary` calling `ui.ShowMap()`" rule, which the accepted design deliberately invalidated: Back to forest stays statically primary and the map is made primary only at run time). It is delegated to `objective_cta_source_check.py`, which is **not a C# parser or compiler** and executes nothing: every rule below is a static, lexical rule over source text. Nothing here is a Unity, native, compile or render result. It reads `LearningObjectivesView.cs`, `ScenarioOneUiRoot.cs` and, through `collect_companions`, every C# file under `Assets/` that mentions `LearningObjectivesView`, `ScenarioOneUiRoot`, `UiKit`, an Objectives header button name, `.Learning` or a `\u`/`\x` escape, also when read with Unicode format characters removed (the other `LearningObjectivesView` partials and `UiKit.cs` among them). Called without those companion sources it fails closed. Within that input it requires (#309 third pass):

- **Lexing it can follow (N-4).** A precise lexer separates comments, preprocessor lines and string/char literals, including interpolation holes, whose code is treated as code. Raw strings, Unicode-escaped identifiers, malformed character literals, line breaks in regular strings and any literal or comment that runs across a preprocessor line fail closed. In `LearningObjectivesView.cs` and `ScenarioOneUiRoot.cs`, which the older regex checks also read, both lexers must agree on every literal/comment boundary. A literal nested in an interpolation hole there therefore fails closed even when harmless. Characters the C# compiler reads differently from this lexer also fail closed (#314 S-2): U+0085, U+2028, U+2029 and a lone CR anywhere in a file, because Roslyn ends a line there (so they can end a `//` comment or a preprocessor line); Unicode format characters (category Cf, such as U+200D, U+00AD or a non-leading U+FEFF) and control characters in code outside comments and literals, because Roslyn ignores Cf inside an identifier; a `#` that does not start a plain directive line, since Roslyn also honours a form feed, vertical tab or no-break space before or after it; and any line of a multi-line literal or comment that starts with whitespace and `#`. Companion files are selected on their text with format characters removed. A lone CR read from disk is already turned into LF by Python's universal newlines; the rule also covers in-memory callers.
- **Exactly one static primary (RR-1, N-1).** The Objectives header (`VisualElement header` … `modal.Add(header)`) is straight-line code in reviewed statement shapes. Exactly three reviewed buttons are each bound by caption, click, enabled argument, classes and name: `Stand map [M]` → `ui.ShowMap()`, no classes, `objective-primary-cta`; `Work Plan [Tab]` → `ui.ShowWorkPlan()`, no classes, `objective-work-plan`; `Back to forest [O / Esc]` → `ui.CloseAll()`, `true`, `btn-primary`, `objective-back-to-forest`, which must be in `GuidanceButtonNames`. Extra header buttons may be added only if non-primary, added once, with a new caption and a name outside `GuidanceButtonNames`. This conservative rule freezes the reviewed header; it is not a UI policy. Every use of `header`, `buttons`, `modal`, `Root`, the constructor's `ui` parameter and each button local must be one of those shapes. A `+=`, cast, alias, lambda, interpolation hole, `if`/`goto` wrapper, indexer, `SetEnabled`/`Clear` or later restyling of a header element therefore fails. Across the view class and all its partials the checker requires exactly one `btn-primary` literal (Back to forest's). It also requires no class-list API, no element-tree traversal or query (`parent`, `hierarchy`, `Children`, `ElementAt`, `panel`, `visualTree`, `contentContainer`, `Q`, `Query`, `UQueryExtensions`, `RootElement`, `rootVisualElement`, `GetFirstAncestorOfType`, `GetFirstOfType`, `FindCommonAncestor`), `Root` only in its declaration and the constructor, one constructor, and no `[Conditional]` or `using static`. Every `UiKit` call must be a reviewed member with plain-literal class arguments; an alias or method group fails.
- **Pinned guidance code (RR-2, RR-3).** The bodies of `RefreshNextActionGuidance`, `ClearNextAction`, `ApplyNextActionGuidance`, `GuidanceVisible`, `CloseHelp`, `SetScreen` and `ShowMap` must equal the reviewed text in the scanner token for token (comments and layout ignored), carry no attribute and contain no `#if`. `LateUpdate` must start with the apply. Outside those bodies, `helpClosedFrame`, `nextAction`, `guidanceCandidate`, `guidanceScope`, `guidancePrimaries`, `GuidanceButtonNames`, `ApplyNextActionGuidance`, `ClearNextAction`, `GuidanceVisible` and `learning.Root`/`Learning.Root` may appear only in their reviewed declarations and statements, each exactly once. A qualified (`this.x`, `Type.x`), tuple, `ref`/`out`, lambda, shadowing, `nameof` or count-compensated reference therefore fails. The `learning` field may not be reassigned, aliased or passed on. The related state `help`, `manager`, `learning`, `map`, `workPlan`, `review`, `rackLayout` and `screen` keeps its reviewed number of writes and, since #314 S-1, its reviewed write *sites*. Each field declaration is pinned as a direct member of the `ScenarioOneUiRoot` class body (#320 N-2, below). Each reference is written only by its one reviewed statement, which must be a top-level statement of `Start` (not wrapped, deferred, moved or inside `#if`), and `Start` may not `return`, `throw`, `goto` or `yield` before the last of them. `screen` is written only by its initialiser and the pinned `SetScreen` and `TryShowReviewYear` bodies. Any other write of one of the following lexical shapes fails, whatever the count, in ordinary code and (since #320 N-1) inside interpolation holes: an assignment or compound assignment, `++`/`--` (prefix too), a `ref`/`out`/`in` argument, a parenthesised, tuple or nested-tuple target, `__makeref`, or any use through a receiver other than `this`. Writes the checker cannot see lexically (reflection, L-04) are not covered. `screen`, a value type, may not be a member receiver or a whole call argument, so no `ref this` or `in` helper can write it; `unsafe` code is banned in the root; and no reviewed snippet may lie inside `#if`. Outside the pinned bodies a class-list call must name a plain, non-primary literal, the root's 5 `btn-primary` literals must all be inside them, and Objectives header names may appear only in `GuidanceButtonNames` and the pinned routing. `ScenarioOneUiRoot` and `UiKit` must be single, non-partial declarations. No other companion file may name an Objectives header button or reach `ui.Learning.Root`, and in another companion `.Learning` may only be followed by a member access other than `Root` or by `== null`/`!= null`, so the view object cannot be aliased or passed on first (L-06, closed for those shapes).
- **Routing inputs (RR-3, #314 S-3).** The pinned routing reads `NeedsAnnualReview` in the root and `CurrentTopicIndex` and `TeachingRacks` in the view; their definitions are pinned to the reviewed text as direct members of their class (#320 N-2). The game and teaching state they read in turn (`ScenarioOneManager`, `ScenarioOneTeachingSequence`, `TeachingFacts` and the lesson progress, W-DEP-05) and the members of other classes the chain reads (`StandMapView`, `WorkPlanView`, `RackLayoutTracker`) are not checked. - **Interpolation holes (#320 N-1).** The lexer already kept the code of every interpolation hole; the related-state rules above now read it too. In `ScenarioOneUiRoot.cs`, outside the pinned bodies, each interpolated string is opened up and the code of every hole, at any nesting, in regular, verbatim (`$@`/`@$`) and multi-line verbatim holes, inside lambdas, local functions, properties or called methods, is checked with the same write, receiver and `screen` rules as a statement. A hole that contains `#`, or a format clause that starts with `::`, fails closed. Read-only uses (`$"{manager.CashCents:N0}"`, `$"{this.review}"`, `$"{(help, map)}"`) stay accepted. As for statements, `screen` may not be a member receiver or a whole argument inside a hole, and a related-state name after any receiver other than `this` fails, even in `nameof(ScenarioOneUiRoot.map)` (O-13, O-14). Literals nested in a hole are still mostly rejected first by the N-4 lexer-agreement rule.
- **Owning class (#320 N-2).** A text pin used to mean "this exact token sequence occurs once in the file", which a decoy type holding the reviewed text could satisfy while the real member changed. A bounded token walk now records which brace opens a namespace, a type (`class`, `struct`, `interface`, `enum`, `record`) or a block. Every reviewed declaration (the related-state fields, the guarded fields, `GuidanceButtonNames`, `Learning`, the routing inputs, the view's `Root`, `UiScreen`) must be a direct member of the top-level class body with no attribute or extra modifier in front; the other reviewed statements must lie in the class itself, not in a nested type; and each pinned method and the Objectives constructor, `Refresh(bool)` and `Start` must be direct members of their class. Comments are not tokens and a preprocessor line is one opaque token, so neither can provide a declaration. Unbalanced braces, braces that `#if`/`#elif`/`#else` branches do not balance, and a file-scoped namespace fail closed. Because simple-name lookup prefers names declared closer, the walk also rejects, in the root and in every part of the view: a type nested in or added to the file with a name that the reviewed text looks up (`Time`, `StandaloneSessionMenu`, `ScenarioOneTeachingSequence`, `UiKit`, a local's name ...); a member of the class named like an outside type the reviewed text reads (for example `private FakeTime Time`); and a `using` alias with such a name. The root's class header must stay `public sealed class ScenarioOneUiRoot : MonoBehaviour`, and no part of `LearningObjectivesView` may add a base type, since a base class's members would hide those names too. Unrelated nested and additional types stay allowed. The member-name scan is lexical (the identifier before `(`, `=`, `=>`, `{`, `;` or a top-level `,` in a member header), not a C# declaration parser.
- **UiKit (N-3).** `UiKit.Button`, `Box`, `Row`, `Text`, `Add` and `MakeModal`, every member the Objectives constructor calls, are pinned and declared once; `UiKit.cs` contains no `btn-primary` literal.
- **Reachable caller (RR-3).** The view class calls `ui.RefreshNextActionGuidance()` exactly once, as a top-level statement of `Refresh(bool)` after its single reviewed early return, with no other `return`, `throw`, `goto` or `yield` in that method.
- The per-statement checks retained from #304: the exact `Stand map [M]` button wired to `ui.ShowMap()` with one literal name, added to the header row and never otherwise used; the map selected as target exactly once in the pinned routing text, for an unconfirmed Rack V2 Objective 1 as far as that text and its pinned UI inputs decide (the game state they read is not checked); ordering, the scoped demotion loop and the Help, Reference preview, session-menu, help-close-frame, enabled, visible and in-scope guards. A failure of the `GuidanceButtonNames` allowlist itself (duplicate, non-literal, `#if`, extra or qualified reference) is reported as that error rather than as a membership failure (RR-5).
