## 1. Outcome, sequencing and boundaries

The first useful outcome is **not** a new architecture library. It is visible, verified player-facing progress along **two independent paths**: (i) owner-accessible Compact30 with its **correct authored no-rack scene** and the original five-rack **established Unity menu/UI/management loop**, and (ii) Multi [#849](https://github.com/jermur788/CCF/issues/849) genuine one-area **2D select → pending → approve → atomic Fell → Year+1**. Neither waits for the other, a central abstract `ScenarioManager`, a unified growth model or browser text deployment. The present #820 71/71 bounded native tests do not verify default scene entry or fused #836 art/gameplay; Multi G2/A1 remains unmerged and the 2D adapter is a separate candidate. See [3D source map](https://github.com/jermur788/CCF/blob/Scenario-One-shared-ccf-foundation-architecture-source-audit-20261120-v1/Docs/Handoffs/ScenarioOne-Shared-Foundation-Architecture-20261120/Scenario-One-CCF-Shared-Foundation-Source-Mapped-Architecture-Draft-20261120.md) and [Multi #730 A–E](https://github.com/jermur788/CCF/issues/730#issuecomment-7026958964).

**Gates before production:** this DRAFT is independently reviewed, #425 resolves relevant G4 conflicts, owner resolves material G5 choices, relevant feature specs are APPROVED where required, actual source owner and physical Ops permissions are registered, and any Unity use respects one machine-wide live lock. This plan does not itself allocate a worker, branch, file or Editor slot. **Windows build requires prior owner playtest of exact qualifying Compact Editor candidate and separate owner build permission.**

## 3. Detailed small-step approach and scope control

### 3.1 Current Unity path (reuse before abstraction)

1. **Read the exact combined candidate** chosen by #844 and enumerate real current scene/start/menu/manager/canvas wiring; compare with the original five-rack main source. Treat #820 and #836 as **diverged** until actually integrated in one authorised lane.
2. Preserve the historical five-rack **`ForestTest`** system and all old saves. A thin, validated scene/binding seam may be warranted if the observed failure is only *entering the correct scene*, but do not generalise scenario identity/saves by convenience. Source guards must decide absent rack functions—not hide a functioning manager and claim success.
3. Demonstrate one specific player path: open correct scene → inspect/move/mark/plant actual tree positions → pending 2 Oak+2 Beech owned-stock orders → Work Plan approve → annual resolution and authoritative review; only actual results count.
4. Verify a **negative** compact case (no rack UI, rack lessons, ghost extraction route or false H1 Fell/revenue) and **positive** old-world case (real Rack V2/MFM). Leave the old UI and compatibility checks intact. The rest of full-loop/completion qualification is separately owned.
5. Only after a verified concrete duplication, plan a *small* cross-scenario capability binding; document which existing files and test contracts require change. Avoid structural renaming for its own sake.

### 3.2 Current Multi 2D path (independent engine)

1. Preserve [Multi A1 exact source](https://github.com/jermur788/CCF/commit/4bb809732fb691f15630e1fbc5ea20dca6dbbe2f) as its own qualified **side-branch** authority, not main/Unity integration. Current 2D source/player contract in [source-fenced proposal](https://github.com/jermur788/CCF/blob/docs/multi-player-session-adapter-contract-20261119-v1/Docs/Handoffs/MultiRack-Simulation-20261116/Multi-Player-Session-Adapter-Source-Fenced-Contract-20261119.md).
2. One root lock must provide the **same immutable snapshot** for `WorkSourceToken`, exact-case `TreeId`, current committed frame, pending/approved plan and event ledger. Proposed separate `PlanStateRevision` must be explicitly reviewed/approved before implementation and never silently mutate `WorkRevision` semantics. No second game-state store inside map UI.
3. Renderer choice follows source suitability and user-visible quality, not pressure to compile-link Unity files. If using Scenario One map logic, first obtain complete transitive dependencies/new V-01 permission including `MapTree.TreeId` remedy and exact source-ownership review; otherwise implement a minimal standalone renderer grounded in shared world-metre/north-up symbology.
4. Keep unavailable features truthfully disabled, including G1 `DISABLED — Manual/NotCovered` and economics `UNAVAILABLE`. A map click cannot implicitly Fell.
5. After actual source/UI compile and targeted negative tests, seek independent review. Do not extrapolate one 100-Sitka area to multi-area/rack simulation.

### 3.3 Single existing browser authoring path

1. Inspect the editor's **current actual coverage** (79 pages / 278 records) and the specific original/candidate source variants; do not call empty later-scenario tabs shipped copy or a complete string inventory.
2. Reconcile proposed field IDs/provenance/condition with the existing `ccf-cross-scenario-text-editor-v1` **DRAFT** rather than fork the tool. Author can see `[SCENARIO INTRODUCTION]` in **dev preview only**.
3. Require reviewed, versioned Git content approval and typed formatter/token validation before any runtime resolver. Runtime year/tree/DBH/work/cost/results are read from engine state, not freely authored strings.
4. Gate text fallback by actual profile/scene/variant (including no-rack and legacy); missing required text has a release-blocking or approved safe fallback verdict, never silently ships placeholders. Preserve old copy and protected gameplay IDs.
5. Qualify through actual browser-editor interaction, negative import/export/token cases and 3D 720p/1080p UI + later native 2D display if a resolver is approved. This browser/GitHub author ran **none** of those tests.

## 5. Qualification, review and end state

**P0 document checks:** direct binding handoff/source links, trace owner principles and Multi A–E, reconcile D-083/84/85 and D-078/79/81, diagram/status consistency, DRAFT markings, four-file schema and five-file GitHub allowlist. Final #850 Markdown handoff with readback/compare. **No Unity/Node/2D/browser game test.**

**Future P1 feature qualification (separate actors):** targeted source/negative checks (Tier 1); exact candidate source + authorised native 3D/2D visible player path and focused saves (Tier 2); full combined milestone/owner acceptance only at the proper later gate (Tier 3). Compilation/source commits alone do not prove playback, rendered GUI, reference conformance or completion. Independent nonauthor review when required; implementation → reviewed → integrated → verified → accepted remain distinct.

**Stop conditions:** conflicting live writer/physical lease, unapproved save mutation, direct Multi↔Unity source copying, unqualified scene/roster, missing signed Compact policy, branch drift, unknown dependency closure, or any demand to claim an unrun test. Stop only affected task and continue authorised other work. If this architecture would delay the two current real playable paths, defer it.

**Planned disposition:** a consolidated **DRAFT ready for independent nonauthor review**, **not** an integrated shared game or approval. See [tasks.md](tasks.md) for future scoped packet proposals and [checklist](checklists/requirements.md) for unchecked acceptance.
