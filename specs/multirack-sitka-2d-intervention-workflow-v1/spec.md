## 1. Product intent and interpretation

Build the *actual* forestry-intervention loop in the separate 30 × 30 m, 0.09 ha, closed 100-Sitka synthetic 2D laboratory. Player judgement is demonstrated in an inspected sample; any scaling to other locations is an explicit, reviewable proposal for **provably comparable current** conditions only. A proposal cannot become Fell, or change tree biology, simply by being displayed or locally annotated. Only a subsequently approved Work Plan may authorise one controlled real execution, after which every later annual step uses the actual living survivors and retains the historical reason and result.

**Authority categories must not be conflated.** The following principles are accepted Scenario One intent, but their transfer into this unrelated synthetic lab is a **2D design proposal pending approval**, not already accepted Multi behaviour or an Irish forestry standard. This document specifies a proposed contract, not observed software capabilities. There is no assertion that Stage 4, #811, Stage 5, source execution or an actual historical five-rack Unity workflow has been qualified here.

## 3. Proposed player experience and state machine

1. **Inspect current committed stand.** Show year, experiment/source identity, 100 original IDs with current live/dead status, local competition and evidence availability. Select a local sample explicitly; annotate actual player decisions for living trees, including **why** to remove a competitor or retain a desirable tree. Read-only inspection is always available, including terminal/no-work states.
2. **Demonstrate a sample.** The player chooses exact current source IDs and removal/retain intentions in an explicit bounded local neighbourhood, not an arbitrary automatic one-tree rule. If no defensible representative neighbourhood can be formed, require manual tree-by-tree selection; do not call it a qualified sample. Neither sample selection nor marking mutates biology or counts as executed felling.
3. **Propose treatment.** Derive only an explainable, limited rule from the player's reviewed sample decisions and actual present features. Show source sample ID set, cycle/year, coverage boundary, eligible/excluded/manual trees, rationale and uncertainty. A candidate is a **proposal** (not Fell) even if red in a local mock-up; do not use red Fell semantics without an actual work result.
4. **Check comparability.** Offer extension *only* to individually inspectable current areas/trees that pass an approved, source-verifiable similarity predicate. For V1, absence of measured terrain, rooting, wind, historical rack service or credible neighbourhood metrics must not be replaced with plausible defaults. Same species and age alone cannot prove equivalent density, competition or treatment need. If no approved proof exists, the extension action is disabled and those areas remain **MANUAL / NOT COVERED**. The user can still author manual work.
5. **Review and approve prescription.** Display all exact proposed tree IDs, source sample, each matching or excluding reason, projected removals, current/source age and competitive context, and ecological/economic effects as evidence-backed or **UNAVAILABLE**. Player can accept/reject individual proposals and replace them with manual, valid selections. Out-of-sample Crop Tree *quality* is never automatically assigned; any 2D retained-tree candidate is only a suggestion until separately inspected/confirmed. Explicit prescription approval creates or reconciles **pending ordinary work orders with source provenance**, but does not commit or kill trees.
6. **Work Plan commitment.** A separate Work Plan displays pending orders, actual source year/IDs, current validation, performer/cost only where genuinely implemented, cancellations and optional no-work. Player explicitly approves the **whole work batch** after final revalidation. Only this approval is the commitment authority. There is no approve-on-year-advance and no hidden approval from a single Mark click.
7. **Execute exactly once.** Authoritative executor consumes one unique approved batch and applies only eligible real Fell operations in a single atomic current-year state transition, with execution result and history committed together. After a success, a repeat submit with the same execution key yields a recorded already-executed/no-op response, never another Fell, charge or event. On failure/refusal, **zero** trees, counts, cash and history change.
8. **Review and repeat.** Display pre/post live count, basal area and any genuinely available other measures, tree-level results and year-specific provenance. Annual ecological stepping subsequently runs on the real survivors. The next management cycle must re-inspect a **new committed year**, form a new representative sample or choose manual work, and not silently replay older prescriptions. A no-work year remains a valid, explicit choice and produces zero Fell events.

### 3.1 Normative proposed workflow states (require product approval)

- **READ_CURRENT:** source-only active committed frame; may inspect, no work edit if source admission fails.
- **DRAFT_SAMPLE / DRAFT_MANUAL:** user-authored current-year tree choices; local candidate preview may suggest items but has no authority.
- **PROPOSED_TREATMENT:** hypothetical list and comparability evidence; read/revise/reject without mutation.
- **REVIEWED_PRESCRIPTION / PRESCRIPTION_APPROVED:** distinct explicit user action freezes a reviewed revision; creates/reconciles *PendingWork* ordinary orders, never Fell. New edits invalidate approval until reviewed again.
- **PENDING_WORK:** tentative source-bound orders; cancellable with author action; cannot execute.
- **WORK_PLAN_APPROVED:** one explicitly authorised immutable batch revision awaiting controlled actuation. Must revalidate at approval *and* execution; destructive cancellation/replan requires explicit warning and safe policy for already-approved-but-not-executed work.
- **EXECUTED / FAILED_OR_REFUSED / CANCELLED / NO_WORK:** exact outcome; executed removals/history are immutable; re-executing or deleting executed work is impossible. Failed/refused authorisations are not effective approvals and must be revised against current source.

An implementation may choose different internal class names only if it proves these distinguishable states and irreversible boundaries. Stage 5 approval is neither the #805 local candidate operation nor a new alternate biological executor.

## 4. Functional requirements — proposed pending approval

- **FR-01 — Current-state source:** all planning, eligibility, revision keys and execution bind to one accepted source-proved committed Genesis/AfterMortality year, experiment, original fixture, generation/revision where available and exact living tree rows. A diagnostic tab or refused source cannot issue work.
- **FR-02 — Player judgement:** player explicitly chooses sample location and live trees, records retained/release intention and can conduct manual selection without applying a sample to the whole stand. No mandatory perfect marking set or unqualified sample.
- **FR-03 — V1 spatial G0:** recommended default is **NO extraction-rack-planning subsystem** in 2D; represent sample with an explicitly selected neighbourhood/2D outline and extend via reviewable individual current-tree selections, not persisted rack corridors. This is a **PROPOSAL, not approved by D-064/071**. Owner must choose G0 before any 2D zone/rack source authoring. No fake racks if G0 is unresolved.
- **FR-04 — Comparable-only:** transfer requires source-verifiable and reviewer-accepted condition match (species plus relevant current diameter/stocking/local competitor/spacing context and any explicitly known site facts). Quantitative thresholds/algorithm require a separate G1 calibration record. Unknown/non-matching conditions are Manual/NotCovered and must not be auto-filled. Distinct conditions permit separate player sample/manual prescription, not fabricated site classes.
- **FR-05 — Proposal separation:** no proposed candidate is a red Fell mark, dead tree, actual CropTree declaration, Work Plan commitment or executed work; no biology/economy/official history changes in planning screens.
- **FR-06 — Review and provenance:** show source sample/year, per-tree rationale/exclusion, quantities, exact IDs and provenance labels (observed / derivation / gameplay calibration / unavailable). Individual accept/reject; player-authored choices supersede recommendation. No unsupported tree-quality or price claim.
- **FR-07 — Two approvals:** prescription approval creates/reconciles PendingWork only. Separate Work Plan batch approval is the **sole commitment gate** and cannot be inferred from time advance, mode switch, click or imported candidates.
- **FR-08 — Whole-batch validation:** at both approval and execution, atomically reject stale year/revision, missing/untrusted source, duplicate within batch, nonexistent/non-live ID, changed status/quality/area source, conflicts with already approved work, lack of player approval, illegal status, or unsupported executor; no partial felling.
- **FR-09 — Exactly-once transaction:** authoritative executor owns Fell, counts, any money, and append-only work events together under unique source-year + plan-revision + execution identity. Same key replay = no-op/readback; different key trying to fell an already dead or previously executed tree = refused. Crash recovery across process boundaries is *not claimed* without separately approved durable ledger/Host/save design (G3).
- **FR-10 — Replans and locking:** before execution, pending proposals/orders may be changed only through explicit cancellation/review/reapproval; after any executed removal, the executed record and tree identity are immutable, and no later cancellation may resurrect them.
- **FR-11 — Annual sequencing:** work is an explicit current-year actuation, **never** a hidden part of no-work/year-advance. The exact place of work relative to annual growth/mortality must be source-audited and selected in G2; do not graft a new growth path or alter no-work oracle. After execution the next actual annual simulation starts from actual survivors, not a preview frame or old count.
- **FR-12 — Historical review:** each committed year records source tree IDs/sample coverage/prescription version, proposed-versus-approved-versus-rejected distinctions, actual work and result/error, and source provenance; can compare previous cycle with current. Historical views read-only, no editing past decisions or retroactive work. No-work years distinctly represented, zero-work year does not invent harvest revenue.
- **FR-13 — Honest economics:** use real source price/cost and money only if existing authoritative Multi source exposes them; otherwise show unavailable, do not copy Unity timber economics or invent compensation/charges. Any future economy module needs independent authority and tests.
- **FR-14 — Terminal and failure:** last-survivor fell (if otherwise authorised) can reach zero live; no next-year biology resurrection, no phantom Fell or Dq/height=0 values. An engine refusing zero-survivor execution must report a specific safety policy for product decision rather than silently dropping it. Wrong-year/stale/retry/errors keep original stand and history exact.
- **FR-15 — Accessibility:** keyboard, touch and accessible name/role/state for every proposed action, ordered ID list and approval confirmation; do not rely on red/blue alone; 360 px and 200% zoom layouts, useful focus/restoration, error announcement.
- **FR-16 — Boundary:** no frozen original, private Fixture/HTML, #789 no-work baseline, #805 file, S1 Unity work, Host/save/profile, Reference Future, Legacy40, physical Ops, or main integration changes under this DRAFT.

## 5. Data and execution contracts to prove before source

**Proposed source-bound immutable records, not approved ABI:**
- *SampleRecord*: experiment/source identity, committed year/revision, selected tree IDs, explicit player decisions and local conditions evidence, spatial outline/neighbour selection, sample validity and rule vocabulary version.
- *ProposalRecord*: parent sample+revision, target exact IDs, current conditions, match/exclude/manual reasons, reviewer actions, comparison methodology/version, source provenance and current source binding; immutable once submitted for review.
- *PendingWorkOrder*: proposal or player-manual provenance, exact ID, action Fell or eligible other separately approved action, author approval history, no direct mutation.
- *WorkPlanRevision*: unique batch identity, same current source identity/year, exact non-duplicated action set, affordability/execution availability, explicit approval event and unchanged-content digest.
- *ExecutedWorkEvent*: unique execution key, atomic success/rejection, exact tree identities, before/after state where source supports it, cause Fell versus biological mortality, costs if real, source sample/prescription, current year. Append-only and auditable.

All records must be constructed through an audited implementation seam; this spec does **not** authorise writing a JSON API, persistent format, browser storage, arbitrary hash or new CLI switch. The #805 read token and candidate undo stack are never a durable work ledger. For process crash/timeout during transaction, absent a source-proven atomic commit/replay seam the operation must refuse deployment, not pretend exactly-once.
