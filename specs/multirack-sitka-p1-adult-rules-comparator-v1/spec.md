### 5.2 Proposed annual transaction, work and replay grammar (C-1/C-1A)

Candidate immutable event envelope: event-schema version, contiguous sequence, kind, source/initialization identity, command ID, ecological year before/after, expected forest revision, previous-event digest, pre-state hash, ordered typed payload and post-state hash. Genesis commits the input/algorithm manifest. Proposed SHA-256 history digest hashes a `P1-HISTORY-V1` domain tag plus canonical envelope bytes excluding its own digest; state hashes use a separate `P1-STATE-V1` tag and canonical full state, including plan approval/session fields where present, excluding the history tip to prevent a cycle. Exact byte layout requires future C-1 independent review/golden examples. P0's snapshot hash is **not** retroactively redefined as this history digest. Hashes detect corruption relative to trusted input; an attacker able to rewrite the entire local chain can rehash it. No cryptographic authorship/signature claim is made.

**Hash field membership (m-D, proposal for C-1 review).** Pre/post state hashes cover state only. The history digest covers envelopes, which contain those state hashes. State never contains the history tip, so there is no cycle.

| Field | Persisted P1 state / `P1-STATE-V1` hash | Biological projection | History envelope / `P1-HISTORY-V1` digest |
|---|---|---|---|
| Per-ID trees (status, DBH, H, crown, age, XY, provenance) | Yes | Yes (biological fields only) | Through post-state hash |
| Ecological year, growth/RNG model versions, seed, fixture/initialization identity | Yes | Yes | Through post-state hash |
| Plans, stages, base revision and `ApprovalSessionEpoch` on approved plans | Yes | No | Through post-state hash and event payload |
| **Current** session epoch | **No**: runtime only, as in P0, where only approvals carry an epoch | No | Only where an event payload records it |
| Command-ID dedup index | **#562 proposal: No** (rebuilt from history on load; T-10, §9.4). The earlier draft said Yes | No | Yes: every command-originated envelope carries `commandId` and `commandDigest` |
| Death/felling ledger (IDs, causes, years, roll inputs) | Yes | Yes | Through payload and post-state hash |

Consequences:
- An audit-only `ExecutionRejected` changes **no** biological value and extends the history if the event is permitted. **#562 technical proposal (§9.4), still OPEN C-1 until independently reviewed:** a *recorded* rejection consumes its command ID; a *refused* request records nothing and consumes nothing; the dedup index is rebuilt from history and is not in `P1-STATE-V1`, so an audit-only rejection leaves the state hash unchanged (as P0's `PlanExecutionRejected` does) and changes only the history digest. Golden vectors G-01…G-08 separate this from the not-consumed alternative.
- A `PlanStale` event changes state (plan stage) and history.
- A P0-like conditional load with no open plan changes neither.
- An always-on `SessionLoaded` variant, which is not proposed here, would change history only.
- Deterministic across reload: every state field above and every recorded envelope. A fresh current epoch is not hashed until a later approval records it.

Mode A raw-history equality is still required **only** for complete identical canonical histories. No hash policy is adopted by this table.

Proposed commands and transitions:
- `CreateExperiment` records verified fork and initialization once. P1 plans follow Draft→Proposed→Approved→PendingWork→Executed, with explicit Rejected/Cancelled/Stale terminals. Marking/proposing/approving/queueing never changes living N/BA. Ordinary action eligibility is Live plus current authoritative DBH at or above the imported threshold, compared without annual integer-mm rounding; biology always includes all living. Reservation conflicts, duplicate IDs, stale revisions and absent/dead IDs reject execution atomically. A new proposal/approval is needed to replace a stale terminal plan; approval cannot be silently resurrected.
- `ExecuteWork` validates the whole exact reserved set, current forest revision and current session epoch, then records felling at **current DBH and current ecological year**, with plan provenance. No partial execution or natural-death timber/reward is introduced. An audit-only `ExecutionRejected` may append if safe; its pre/post biological state is identical. Invalid files cannot append to an untrusted chain.
- `AdvanceAnnual` stages a copy, validates expected revision/year and command ID, then records one atomic **`P1AnnualAdvanced` compound event**: increment year; compute competition from post-work living set; grow and age; relax crowns; calculate post-growth density/hazard using stored pre-growth CI; gather hazard then boundary victims using source suppression/ID priority; apply each natural death once; finish metrics; stale open approved/pending plans by reason. Death entries are child records of this event, **not additional mutation events replayed a second time**. Source biological cause stays `self-thinning`; `hazard`/`boundary` are mechanism annotations. Natural-dead reserved IDs invalidate affected draft/proposed plans as well; record ID-specific `ReservedTreeDied` before the general annual-revision stale reason, at most one terminal transition per plan, sorted by plan ID. These plan rules are lab design, not a claim that CCF/P0 already implements them.
- `Save` serializes a consistent committed snapshot+full ledger+tip. `Load` first validates/replays in detached state from trusted genesis, recomputes annual results from pinned model and verifies all payload/state/digest fields, compares saved snapshot, then atomically activates. No fallback to unknown model or fresh seed. Failed validation/commit leaves year, trees, plans and active tip unchanged. For **successfully committed commands**, a retry with identical ID/payload returns the existing result without another advance; same ID/different payload refuses. **Rejected-command ID consumption and retry behaviour:** #562 proposes the §9.4 policy (recorded outcomes consume the ID; identical retry returns the recorded outcome; different payload refuses `CommandIdConflict`; refusals consume nothing), still OPEN C-1 until independently reviewed; a rejected attempt cannot advance biology. Rebuild the dedup index from the replayed history. Save outcomes must distinguish: pre-rename write/file-fsync/rename failure `SavePrecommitFailed` (old final bytes preserved; clean only own temp); rename followed by successful directory `fsync` `SaveCommittedDurable` (operation-confirmed under reviewed filesystem policy); and rename succeeded but directory `fsync` failed `SaveCommittedDurabilityUnknown` (**new final bytes already installed, crash durability unconfirmed; no rollback or old-file preservation claim**). A subsequent list-refresh failure is `SaveCommittedListRefreshFailed` rather than a save rollback; a lost HTTP reply is `OutcomeUnknownToClient` until command-ID/save readback, **never grounds for rerunning the annual biological command**. These remain unapproved DRAFT result names, not an `fsync`/power-loss test PASS or a rollback of in-memory biology.

**Proposed P0-like conditional stale-on-load option (C-1A owner-CONFIRMED initial-experiment policy D-082; M-4):** after successful detached validation, create a fresh session epoch and append exactly one `PlanStale(SessionLoaded)` per open Approved/PendingWork plan, in ordinal plan-ID order. **If no such plan is open, the load appends zero events.** This matches P0 `LabSession.FromFile` (`LabSession.cs:76–85, 144–149` at `2659db99`), which appends no other load event; P0 code is unchanged. No duplicate stale is appended for a plan already terminal. Loading the same old file with open plans in two new independent sessions creates two distinct valid histories, not duplicate deaths. An unconditional `SessionLoaded` audit event is **not** part of this option. If a future design wants one, it is a separate unapproved alternative that makes raw-history equality across any load impossible, and it must be put to the owner as such. Epoch is approval authority only, never biological RNG seed. Reapproval requires a fresh legal plan path. Alternative persistent approvals require a separate binding/revocation/security contract and owner decision. P0 policy is unchanged.

Replay of an identical complete event stream restores the recorded session fields; it does **not** simulate another user load or append load events. Live activation on load is a separate operation. Mode A/B compare biological values and **legally equivalent executed work**, not equal event counts or full snapshot/history hashes. In Mode B an uninterrupted branch that executes a still-valid plan cannot be compared as equivalent to a loaded branch where that plan is stale and unexecuted. Use no execution in both branches, or documented fresh legal approval paths producing the same felling set/time. Preserve both actual chains. **Original-fixture trust record (T-02).** One record per fixture, compiled into P1 source so that every change is a reviewed diff:

| Field | Meaning |
|---|---|
| `trustTableVersion` | Version of the whole table; recorded in every P1 experiment header |
| `fixtureId` | P0 fixture ID, verbatim |
| `fileName` | Exact file name, `<fixtureId>.sitkalab.json` |
| `fileByteLength` | Exact expected length in bytes |
| `fileSha256` | SHA-256 of the complete file bytes |
| `p0SnapshotHash` | P0 canonical snapshot hash |
| `p0Format`, `p0SchemaVersion` | `ccf-sitka-lab`, `1` |
| `p0SourceRevision` | Full 40-hex P0 commit the record was prepared from. Provenance only; never queried at runtime |
| `reviewRef` | Where the independent review of this record is published |

The **values are pending**. This DRAFT invents no hash and copies no value from P0's `MANIFEST.sha256`, because that file is exactly what the table must not trust.

Runtime order, all-or-nothing, before any P1 state exists:
1. The requested ID must be in the table; otherwise refuse `UnknownOriginalFixture`.
2. Open the P0 fixture directory with `O_DIRECTORY|O_NOFOLLOW`; open the file relative to it with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`.
3. `fstat` the **descriptor**: regular file, link count 1, size equal to `fileByteLength`. Refuse otherwise, before reading.
4. Read at most `fileByteLength + 1` bytes; any other count refuses (the file changed underneath).
5. SHA-256 of the bytes equals `fileSha256`.
6. `LabFile.Parse(bytes)` succeeds (P0's strict reader and canonical-byte check).
7. `CanonicalJson.SnapshotHash` of the parsed snapshot equals `p0SnapshotHash`, and so does the file's own embedded `snapshotHash`.
8. The original-state rules of §4.1 step 2 hold.

A consistently forged fixture plus `MANIFEST.sha256` fails at step 5. A whitespace change that keeps the snapshot hash fails at step 5 (and at step 6, canonical bytes). The experiment header records `trustTableVersion` and the table's own SHA-256. On every later load the genesis fixture is re-verified against the **current** table. If its record was removed or changed, load refuses: there is no silent re-anchoring.

**Derived capture-fixture catalog (T-03).** A separate compiled-in table and a separate file format, candidate `format="ccf-sitka-p1-derived-fixture"`, `derivedSchemaVersion=1`, suffix `.sitkap1fx.json`. Each record binds: `derivedFixtureId` (always prefixed `p1d-`, a prefix no original ID may use), file SHA-256 and length, canonical content hash, `geometryModel` (`Legacy40` or `Enlarged80`), the declared source area as **f32 bits**, a purpose class (`wiring`, `dense`, `edge`, `singleton`, `tie`), the derivation (source original fixture ID and file SHA-256 when derived from one, or `designed`), the transform ID and version (for example `corner-square-to-centred-xz-v1`), and `reviewRef`. Original import and derived import are **different functions** with different tables. Each refuses the other's IDs and formats. Derived fixture files live in a P1-owned directory, never in P0's `fixtures/synthetic/`.

**Data root and file operations (T-05).**
- Root `.p1-data/` under the P1 tool root, ignored by the **P1** `.gitignore`. It is opened once with `O_DIRECTORY|O_NOFOLLOW`. **(#575, m-8)** Every check below is made with `fstat` or `fstatfs` on that **opened root handle**, never on the path: it is a directory; it is owned by the running user; it is not group- or world-writable; and its filesystem is a **local POSIX filesystem** on a reviewed allow-list, so that owner, mode, link-count and `fsync` results mean something. Refuse to start on DrvFs (`/mnt/c` style mounts), 9p, network mounts and any unrecognised filesystem type, where those fields are not reliable. The initial candidate allow-list is ext4 only (observation: the CCF `Files` volume is ext4 under the repository storage policy; that WSL2 distribution roots are ext4 is background knowledge, not verified here). Any addition needs the file-security reviewer. These are **new P1 requirements**; P0 does not make them.
- Save names: `^[A-Za-z0-9_-]{1,64}$` plus `.sitkap1.json`, never a client path, separator or extension choice.
- Reads: the same descriptor-based sequence as the trust import (open no-follow and non-blocking, classify the **opened descriptor**, cap the size, bounded read). This keeps P0's MULTI-006 behaviour, which already classifies the descriptor with `statx(fd, "", AT_EMPTY_PATH)` before reading (DSC: `NoFollowFiles.cs:96–129`). P1 must reimplement and requalify it, not assume it by copying.
- Writes: serialize fully in memory; refuse if over the cap **before** creating any temp file; then `openat(O_CREAT|O_EXCL|O_NOFOLLOW, 0600)` a temp name, write every byte, `fsync` the file, `renameat` over the final name, `fsync` the directory. Only pre-rename failures unlink own temp and preserve prior file. After rename: dir-fsync success = committed/durable on validated fs; dir-fsync failure = new final installed/durability UNKNOWN, no rollback. Lost reply/list refresh have distinct truthful postcommit/client-unknown statuses (§0). P0 has no `fsync` (DSC: no call in `NoFollowFiles.cs`), so crash durability is a new P1 property that the reviewer must accept or drop explicitly. **(#575)** `fsync` and the root owner/mode checks are reviewer-supported **proposed** P1 additions (#566 Q6), limited to an opened root handle on a local POSIX filesystem as above. They need independent security and runtime qualification and are **not** represented as proven P0 properties.
- Platform: Linux x64 and Ubuntu on WSL2 only, with a P0-style startup self-test of the no-follow primitives. Any other platform disables the file API. There is no path-based fallback.

**Host (T-06).** Bind `127.0.0.1` only, default port 5188 (configurable; refuse to start if busy; never 5187). Keep P0's guard set: loopback client, exact `Host`, exact `Origin` on POST, `Sec-Fetch-Site` same-origin or none, JSON content type, 1 MB request bodies, `Cross-Origin-Resource-Policy: same-origin`, no CORS. **Serialization (T-07).**
- UTF-8, no BOM, LF only, no insignificant whitespace, fixed per-schema key order, ordinal ID order, strict reader (duplicate keys, unknown keys, comments, trailing commas, depth over 16 all refuse).
- Integers are base-10 JSON integers within ±(2^53−1).
- Authoritative floats are stored **as bits only**: `{"k":"f32","b":"<8 hex>"}` or `{"k":"f64","b":"<16 hex>"}`, lowercase, most significant digit first. A decimal string appears only in captures and exports, where it must agree exactly with the bits.
- Every root carries `format` and its schema version. Unknown formats or versions refuse.
- **No wall-clock time** in any save, event, hash or capture record. The session epoch stays random approval authority only, as in P0. Any displayed calendar is derived (`inventoryYear + elapsed`) and never stored as authority.

### 9.3 C-1 proposal: archive layout and capacity (rewritten by #575 F-1/m-9; terms, units and the smallest-event label corrected by #581 N-6…N-8 and N-10)

**Proposal (T-08): compact authoritative archive; full replay on every load; per-ID trace as a separate, non-authoritative export.** Three layouts stay distinct: the **full archive** (every per-ID datum stored), the **compact archive** (authoritative; per-ID values recomputed on replay) and the **trace export** (derived, non-authoritative, never loadable as state). #575 adds **no** incremental-hash or checkpoint semantics to the proposed design; such options appear below only as open alternatives.

What the compact save holds:
- header, trust references, initialization manifest version and hash, and the platform fingerprint (§9.9);
- the current snapshot, with tree values as bits;
- ordered event envelopes;
- for each annual compound event: post-state hash, stand summary (N, BA, Dq, RD, P as bits) and one child record per death (ID, mechanism `hazard` or `boundary`, roll bits, kill order);
- work-plan events.

Load replays every year from the trusted fixture and verifies every hash, as P0 does today (`LabSession.cs:76–83`). A trace export (candidate `format="ccf-sitka-p1-trace"`) re-derives per-ID detail. It records the experiment tip hash it was derived from, carries the C-7 label, and can never be loaded as state.

This section's formula is the **single** model and the §4.1 figures are withdrawn. Each term is an **estimate from an illustrative layout**, counted byte-for-byte from the exact example strings committed in §9.11. The layout is not a schema, and nothing was run in the project.

**Units (N-8).** `MB` and `GB` here are decimal (10⁶ and 10⁹ bytes); `MiB` is binary (2²⁰ = 1,048,576 B); `KB` is not used. The proposed file cap is 64 MiB = **67,108,864 B**.

**Event byte envelope and the event cap (F-1; relabelled by N-6, examples committed by N-10).** Every event envelope (§5.2) carries a `commandDigest`, a previous-event digest and pre- and post-state hashes: four 64-hex strings are 4 × 66 = 264 B once quoted, before keys, the command ID, years, revision or payload. The counts below are of the exact example strings committed in §9.11. They are **examples, not a schema**, and **none of them is a lower bound**:

| Illustrative event (exact string in §9.11) | Bytes |
|---|---|
| E1 descriptive keys, 16-character `commandId`, payload `{"planId":"p"}` | 429 |
| E2 same, 64-character `commandId` | 477 |
| E3 E2 plus a 64-hex `initializationRef` in the envelope | 564 |
| E4 terse one-letter keys, 16-character `commandId`, empty payload — **one example, not a floor** | 333 |
| E5 system event (`commandId` null), descriptive keys, empty payload | 428 |
| E6 terse variant of E4 **without** `year`/`revision` | 321 |

Reproducible bound: **reachable events ≤ ⌊(MaxFileBytes − snapshot − header) ÷ e_min⌋**, where `e_min` is the smallest canonical event. **The smallest legal event is UNDECIDED**, because no schema fixes it, §9.11 commits examples rather than a grammar, and E6 shows a shorter envelope than the "terse" E4. For 5,000 trees (snapshot ≈ 1,210,000 B at 242 B/tree from §9.11 T1) and an assumed 2,048 B header, the available event bytes are 67,108,864 − 1,210,000 − 2,048 = **65,896,816 B**:

| `e_min` | Reachable events | Byte cap binds before 200,000? |
|---|---|---|
| 564 (E3) | ≈ 116,800 | yes |
| 477 (E2) | ≈ 138,100 | yes |
| 429 (E1) | ≈ 153,600 | yes |
| 428 (E5) | ≈ 154,000 | yes |
| 333 (E4) | ≈ 197,900 | yes — by about 1% |
| 321 (E6) | ≈ 205,300 | **no — `MaxEvents` binds first** |

Two thresholds matter, and neither is a capacity guarantee. The **generic** one is 64 MiB ÷ 200,000 = **335.54432 B per event**, before any header or snapshot is subtracted. The **working** one, for the assumptions immediately above, is 65,896,816 ÷ 200,000 = **329.48408 B per event**. So nothing here shows that all 200,000 events are unreachable: that holds only while `e_min` stays above ≈ 329.5 B, and E6 at 321 B is below it. The four digests alone (264 B) certainly do not prove it, since 200,000 × 264 B = 52,800,000 B = **50.35 MiB**, which is under 64 MiB. Consequences:
1. The event cap and the byte cap are **not independent**.
2. The quantitative event cap is **UNDECIDED** and must not be treated as settled. Derive `MaxEvents` from the byte cap and the fixed envelope once P1-03 produces a canonical grammar with committed golden examples, or drop it as redundant and keep only the replay-cost guard below. Until that exists, no claim that all 200,000 events are unreachable is supported.
3. The worst case is a large file of small events (for example repeated audit-only rejections). A realistic experiment has about `Y + W` events, of the order of hundreds.

**Replay cost: every per-event state hash counts (F-1).** The earlier text costed replay as the Hegyi term only. P0 hashes the **whole snapshot after every event**: on append (`LabSession.cs:131`) and again on replay (`Replayer.Replay`, `LabSession.cs:18, 34`; observation at `861b81d3`, source identical to `2659db99`). P1's envelope carries pre- and post-state hashes of a canonical **full** state. The pre-state hash equals the previous event's post-state hash, so it costs a comparison; the post-state hash needs one full serialisation plus SHA-256 per event. Replay therefore has three terms:
- **H1, pair checks:** about N² ordered pairs per year; 5,000 trees × 200 years ≈ 5×10⁹ (upper bound, since trees die). Carried from #562, whose "tens of seconds" was an unmeasured guess.
- **H2, per-event state hash (new):** bytes hashed = E × S, with S the canonical state size ≈ `242·N₀` (242–330 B per tree from §9.11) and E the number of events replayed.
- **H3, history digest:** E × envelope bytes; small.

Estimate of H2 at S = 1,210,000 B (5,000 trees × 242 B, §9.11 T1) and **assumed** serialise-plus-hash rates of 0.1, 0.5 and 1 GB/s. The rates are assumptions, not measurements:

| Events E | Bytes hashed | At 0.1 GB/s | At 0.5 GB/s | At 1 GB/s |
|---|---|---|---|---|
| 1,000 | ≈ 1.21 GB | 12 s | 2 s | 1 s |
| 10,000 | ≈ 12.1 GB | 121 s | 24 s | 12 s |
| ≈ 116,800 (heaviest counted envelope E3, 564 B) | ≈ 141 GB | ≈ 1,410 s | ≈ 283 s | ≈ 141 s |
| ≈ 197,900 (terse example E4, 333 B) | ≈ 239 GB | ≈ 2,390 s | ≈ 479 s | ≈ 239 s |
| 200,000 (P0 constant; reachable by bytes for E6 at 321 B, above) | ≈ 242 GB | 2,420 s | 484 s | 242 s |

This agrees in order of magnitude with the #566 reviewer's estimate (minutes to tens of minutes), which is also **unmeasured**. In the worst case H2 outweighs H1; in a realistic run (E of the order of hundreds) H2 is about 0.6–1.2 GB. At the largest original fixture (2,000 trees, S ≈ 0.48 MB) the same E gives about 0.4 times these volumes.

**Mandatory P1-03 load benchmark (proposed gate; not run).** No cap in this section is accepted before it. It uses synthetic, deterministic load files generated by P1's own writer (never real saves), on each target platform of §9.9. The tree counts are N ∈ {162 (the demo fixture), 2,000 (the performance fixture), 5,000 (the proposed cap)} (existing fixture sizes and the proposed cap; observation), crossed with event counts from tens up to the largest file the byte cap admits, **including the adversarial file made of the smallest legal events**. Per cell it records file bytes, N, E, canonical state bytes per tree and per state, serialisation time, hash time, per-event replay time, total load time, peak memory, and the model-replay time for the Y annual events. The report states the measured rates that replace the assumed 0.1–1 GB/s and the achieved load time against a **replay-time budget the Manager sets**. No budget value is proposed here.

**Refuse or abort, never block (proposed; concurrency fence added by N-3).**
1. **Static pre-check.** After the byte cap and strict parse, and before any replay, compute the planned replay work (`E × S`, and the Hegyi bound from the parsed counts). Above the budget, refuse with `ReplayBudgetExceeded` and leave the file untouched.
2. **Detached replay with a session fence.** Replay runs as a cancellable job outside the live session and checks a deadline and a cancel flag between events. At dispatch the job records the **session identity**, a monotonically increasing **session generation**, the history tip, the forest revision and the save epoch. The generation must advance on any committed history change, **including a history-only audit-only rejection** that leaves the biological state hash unchanged but extends the history digest; otherwise the fence is blind to exactly the commands most likely to interleave. The job derives a detached candidate and applies nothing.
3. **Atomic activation.** Activation re-checks the recorded generation, identity, tip, revision and save epoch **under one exclusive activation/commit gate**, and installs the replayed candidate only if all still match. If a command, audit-only rejection, save, unload or a second load changed the session in between, activation aborts with `SessionChanged` (proposed name). The live in-memory forest, plans, history tip, accepted commands and save bytes are left exactly as they were; no state is partially applied and no file is written.
4. **One load job at a time.** A second load request while a job is in flight is refused with `LoadInProgress` (proposed) rather than run concurrently; the first job may be cancelled explicitly, which returns `ReplayAborted` and activates nothing.
5. **No long synchronous request.** The client polls a job status instead of waiting on one HTTP request.
6. **Runtime guard only.** The deadline and cancel flag never enter a save or a hash, which is consistent with T-07 (no wall-clock data in a save).

**Negative controls for the fence (proposed, not run; fold into N08).** (a) A mutating command commits while a load job replays → activation refuses with `SessionChanged`; the accepted command survives, no state is applied, no disk write occurs. (b) A history-only audit-only rejection during the job → the same refusal, proving the generation tracks history-only events. (c) Two simultaneous load requests → the second refuses with `LoadInProgress` and the first still activates or aborts cleanly. (d) Any refused, aborted or failed load leaves the previous save **byte-identical** and the in-memory forest, plans and history tip unchanged.

The budget value, job API, polling contract and the two proposed class names are **UNDECIDED**: the Manager and the replay reviewer set them after the benchmark.

**Open options that could reduce H2 (not adopted, not designed).** The replay reviewer may weigh: (a) the status quo, one full-state hash per event; (b) hashing state only for events that can change it, with audit-only events carrying no state hash while the replayer re-checks they changed nothing; (c) periodic checkpoint hashes with a history digest on every event; (d) an incremental or Merkle-style state hash. (b)–(d) change the §5.2 envelope and the G-01…G-08 and N08 expectations.

Every command that would exceed a cap refuses **before commit**. A save over the cap refuses PRE-RENAME before temp and preserves prior final bytes; post-rename dir-fsync failures cannot promise prior bytes intact. A negative test must show that the refusal leaves the prior save byte-identical.

**Hegyi pair cost to measure in P1-03.** Source Hegyi CI is an all-pairs loop (DSC: `ForestEcologyController.cs:964–996`). A spatial index is allowed only if it preserves the exact included-pair set **and** the ascending summation order; the source's own comment records a hash change from merely moving the sum into a function (`:990–993`). If load time is unacceptable, the answer is a separately reviewed checkpoint design, **not** skipping verification.

### 9.4 C-1 proposal: command IDs, rejected commands and retries (#556 D-6)

**Source fact.** P0 has **no command IDs** (DSC: `LabSession.cs`). Every click appends events. An execution failure appends one `PlanExecutionRejected` that changes no state, so its post-state hash equals its pre-state hash (`LabSession.cs:229–239`, `Engine.cs:161–167`). P1's command IDs are therefore a new design, not P0 parity.

**Three outcome classes:**

| Class | Examples | Event? | ID consumed? | State hash | History digest |
|---|---|---|---|---|---|
| **Refused request** | Malformed JSON, unknown version, bad ID syntax, size limit, Host/Origin/CSRF failure, envelope `expectedForestRevision` ≠ current (client view stale), over-capacity | None | **No** | Unchanged | Unchanged |
| **Audit-only rejection** | `ExecuteWork` failing a domain rule: plan not pending, stale, cancelled, **plan-base** `RevisionMismatch` or `EpochMismatch`, absent/dead/reserved tree (P0's rejection reasons) | One `ExecutionRejected` | **Yes**, outcome `Rejected` | **Unchanged** (no biology or plan change) | Extended |
| **Committed** | Any successful command | Its events | **Yes**, outcome `Committed` | Changed as the command defines | Extended |

**Two different revision checks (m-1, #575).** (a) The client envelope's `expectedForestRevision` is the client's *view* of the forest. A mismatch with the current revision is a **refusal**: no event, ID not consumed. (b) P0's `RevisionMismatch` and `EpochMismatch` compare the **plan's** recorded base revision and approval session epoch with current state (`P0 Engine.cs:68–71`). In P1 they are domain rules inside `ExecuteWork` and produce a recorded, audit-only `ExecutionRejected`. They are different fields with different outcomes, and G-01…G-08 must not be implemented with the two swapped. The vectors below use plan-base rejections as their audit-only example; their expected results are unchanged.

**Rules.**
- `commandId`: client-generated, opaque, `^[A-Za-z0-9_-]{16,64}$`. Never used by RNG or biology. Its scope is the whole experiment history, across saves and loads. **(#575, m-12) The client mints it.** Every deliberate user action, including a second click after a rejection, gets a **new** ID; only a **transport retry** of the same in-flight request repeats one. G-02 depends on this contract: a client that reuses a recorded ID for a new intent gets the original recorded outcome and changes nothing, so the UI mints IDs per intent, and a client-level negative test (plan N08) checks it.
- `commandDigest` = SHA-256 over the domain tag `P1-COMMAND-V1` and the canonical command bytes (kind, arguments, expected revision). It is stored in the envelope.
- **Retry with the same ID and same digest:** return the recorded outcome (`Committed` or `Rejected`, its event sequence and that event's post-state hash). Append nothing. Advance nothing.
- **Same ID, different digest:** refuse `CommandIdConflict`. No event; the original record is unchanged.
- **A refused request** leaves the ID unused, so a corrected request may reuse it.
- **Check order:** (1) transport, size and syntax checks (refusal); (2) dedup lookup by `commandId` (identical digest → recorded outcome; different digest → `CommandIdConflict`); (3) only then the envelope revision check (refusal) and the domain checks, including the plan-base revision and epoch rules (recorded rejection). Step 2 must come before step 3: a legitimate retry of an earlier committed command carries an old `expectedForestRevision` and would otherwise be refused as stale.
- **One ID per command, not per event.** A command's transaction may append several events (for example a work execution followed by the plans it stales, as P0 does at `LabSession.cs:240–244`). Only the **primary** event carries `commandId` and `commandDigest`; follow-on events in the same transaction carry `commandId: null` and the primary event's sequence number.
- **System events** carry `commandId: null` and an `origin`. Load staling (`PlanStale`, origin `SessionLoaded`) is the only system event proposed. It consumes nothing. This keeps D-082 exact: zero load events when no plan is open, and no command identity is invented for load. Plan staling inside the annual compound event is a child record of that command's event and needs no ID of its own.
- **Dedup index (T-10):** rebuilt from history during replay and covered by the history digest; **not** part of `P1-STATE-V1`. A history in which one `commandId` appears on two primary events is invalid and refuses on load.
- No audit-only event can change biology, plans or the forest revision. The replayer refuses any `ExecutionRejected` whose post-state hash differs from its pre-state hash.

**Golden tests that separate the alternatives** (future P1-03; proposed, not written or run):

| # | Sequence | Expected under this proposal | What it would show under "not consumed" |
|---|---|---|---|
| G-01 | `ExecuteWork(id=A)` rejected → identical retry `A` | History length unchanged; response cites the first event's sequence | A second `ExecutionRejected` |
| G-02 | Rejected `A` → plan becomes executable → identical retry `A` | Still returns the recorded `Rejected`; no felling. A **reused recorded ID never executes**: to fell the plan the client must send a **new** ID, which is a new command (m-12) | The same ID now fells trees: one ID, two outcomes |
| G-03 | Rejected `A` → retry `A` with different arguments | `CommandIdConflict`, no event | Accepted as a new attempt |
| G-04 | Refused malformed request `B` → valid request `B` | Accepted (refusals consume nothing) | Same |
| G-05 | Committed `AdvanceAnnual(C)` → identical retry `C` | Ecological year +1 once; one compound event | Same |
| G-06 | Audit rejection | State hash before = after; history digest changes | State hash changes only if the ID set is in state |
| G-07 | Tampered history with duplicate command ID | Load refuses atomically | Load refuses |
| G-08 | Save → load with an open approved plan → identical retry of an earlier rejected `A` | One `PlanStale(SessionLoaded)` from the load; the retry returns the recorded `Rejected`; no second audit | A second audit |

**Effect on §4 Mode A.** Two runs can have byte-identical raw histories only if they used identical command IDs and digests. That is already in the restricted Mode A condition ("identical command IDs, payloads and hashed state"). No projection or normalized hash is introduced.

**Numeric hazards the capture must expose, not hide.**

Observation (scratch arithmetic from the Class III form at `SitkaGrowthModel.cs:48`, matching the #566 table): `ρ` = 2.860 at ages 0 and 1 (the model uses `max(1, age)`), 1.825 at age 2, 1.518 at 3, 1.288 at 5, 1.126 at 10 and 1.029 at age 28. The store-precision hazard is therefore **confined to ages 0 and 1** (`ρ` > 2). Every original P0 fixture tree has `ageAtInventoryYears` = 28, where it cannot occur, so only a designed small-age vector exercises it and §9.7 keeps one. The capture records stored values; an adapter must not use a shortcut formula; C-2b judges.

### 9.9 Platform fingerprint, save portability and refusal classes (F-2 #575; classes, precedence and options corrected by #581 N-1…N-5) — PROPOSED, NOT ACCEPTED

**Why this exists.** P1 loads by recomputing every year from the trusted fixture and checking every hash (§5.2, §9.3). The growth source calls `Math.Exp` and `Math.Pow` (`SitkaGrowthModel.cs:41, 48, 74, 105`). If a different runtime or maths-library build returns different last bits, a **valid** save would fail replay with a hash mismatch, which an unmodified design would report as corruption or tampering. That risk is background knowledge and **not verified here**; the fingerprint exists to classify it and, optionally, to measure it. P1 targets Linux x64 and Ubuntu on WSL2 (§4), where distribution upgrades change the C library.

**Proposed fingerprint (candidate; field availability not verified; not a schema).** One record in every P1 save header, canonical-serialised like the rest of the file. The **class** column is the N-2 repair: fields are separated by the role they are proposed to play, and **no field is asserted to change an arithmetic result** — that causal question is unmeasured and is exactly what a cross-host comparison would have to show.

#### 9.9.1 Optional probe digest (N-5)

`mathProbeDigest` is **not adoptable yet**. Before it may be used it needs, in one reviewed change: a **fixed, versioned argument list** (`mathProbeArgListVersion = 1`) naming every probed `Math.Exp` and `Math.Pow` argument; the digest domain tag including that version; and a statement of which archive versions require the field. Adoption is then **all-or-nothing per archive version**: a save whose archive version requires the digest but does not contain it, or contains a malformed or differently-versioned one, refuses with `FingerprintMissingOrInvalid`; a save whose archive version does not require it must omit it and is never compared on it (a present-but-unrequired digest is a duplicate/unknown-key structural refusal, not a match). The argument list itself is **UNDECIDED** and no value is invented here. Equality remains a bounded probe over the listed arguments only.

**Refusal classes (distinct; proposed).** None is reported as tamper unless the fingerprints are equal and replay still fails.

**Evaluation order (N-4, proposed; one outcome, no mutation on refusal):**
0. **Before opening any file**, require supported OS/filesystem/no-follow and all mandatory locally observable fingerprint capabilities; otherwise `PlatformUnverifiable`.
1. **Strict canonical JSON/root/field structure**: malformed or truncated JSON, duplicate/unknown keys, wrong root/type and noncanonical bytes cause **structural refusal** (`StructuralInvalid`, proposed name), never a fingerprint mismatch.
2. **Format, archive and fingerprint-schema versions**: unknown/legacy versions cause `UnsupportedVersion`; a genuinely pre-fingerprint archive is not a current-schema missing-record error.
3. **Non-waivable recognised model/algorithm/RNG/source and reviewed fixture-table ID/digest/version, exact genesis/original-file/snapshot or derived-tag/geometry/transform/area, and archive/history integrity**: unknown/removed/reanchored identity or corrupt data causes **trust/compatibility refusal** (`SourceOrGenesisIncompatible`, proposed umbrella name; `UnknownOriginalFixture` for unknown original ID), never an option-A/A′/B/C platform concession. A class-B transition requires a separately approved versioned rule.
4. **Current-version, syntactically well-formed fingerprint record**: absent or invalid value/field type/width/required member causes `FingerprintMissingOrInvalid`; duplicate/unknown keys and truncated JSON were already structural at step 1.
5. **Only after trust** apply a selected comparison of class-A fingerprint identities → `PlatformFingerprintMismatch` where required; class-C diagnostics never mismatch on their own, and B never waives class B.
6. **Detached replay and hash checks** → `ReplayMismatch` (equal compared platform fields) or `ReplayPlatformMismatch` only in the scoped option-B case, then one atomic activation only after all gates. Exact API names and portability policy remain C-1/owner OPEN; no file/session changes on refusal.
