## 3. Player workflows

**W-01 — Start a new independent forest.** A player explicitly chooses O1 or O2 before a new forest is committed. The chosen scenario supplies the correct authored starting world/definition and active save slot; starting fresh does not delete or overwrite either existing save. O2's actual scene/setup and multi-cohort fixture require a later separate approved model/scene packet; a label switch alone is insufficient.

**W-02 — Save/continue the selected forest.** Save and Continue/F9/F10 load affect the **currently selected** scenario's slot only, with an understandable confirmation before a save replaces that scenario's own existing current file. After launch, switching chapters or re-entering one cannot inherit a previously active chapter's trees, cash, inventory, orders, ecology, annual reviews or elapsed years. No automatic cross-scenario transfer.

**W-03 — Reject a foreign/invalid file.** If an O1 file is offered in O2, or an O2 file in O1 (including a copied/renamed file), reject it **before** changing the live world, scene, geometry, money, work plan, tutorial state, timeline, visuals or selection. Give a truthful message naming expected and found chapter where safely readable, without claiming recovery or corrupting data.

**W-04 — Historical O1.** Continue/Load accepts valid O1 historical v1–v24 formats by their documented version/legacy rules, including v1–v9 without scenarioOne, v20/earlier Legacy40 and the frozen v12 Reference Future under its separate trusted preview route. No on-load rewriting of the source file, archive or protected reference hashes.

## 4. Proposed bounded identity and file policy (review-required)

| ID | Proposed rule | Reason |
| --- | --- | --- |
| SI-01 | **Only two recognised chapter IDs in v1**: literal "scenario-one" and proposed literal "scenario-two" (O1/O2 display titles may differ). Reject null, blank, unknown, case-variant, duplicate or inconsistent IDs; no arbitrary filename from user input. Before approval confirm O2 ID does not conflict with an actual authored definition. | Explicit allowlist prevents accidental path aliasing. |
| SI-02 | Keep **O1 exactly** at Application.persistentDataPath / forest-save.json; its .tmp and .bak remain beside it. **Never rename/move/migrate/auto-import** existing O1 files into another name. | Accepted preservation of current devices. |
| SI-03 | Proposed O2 file: Application.persistentDataPath / forest-save-scenario-two.json, with its own .tmp and .bak. Case-sensitive fixed code mapping; no directory traversal, user-generated path or multi-world list infrastructure. | Additive, obvious and non-colliding. |
| SI-04 | Introduce an explicitly serialised **top-level chapter identity** for new multi-scenario files (exact field/version subject to source-owned implementation review); validate raw JSON presence/type AND parsed canonical value. A current new save should also bind any nested management scenario ID when that contract exists. Never infer chapter identity solely from file name or default-initialised JsonUtility fields. | The present nested field is absent in old files and may default on omission. |
| SI-05 | Classify v1–v9 files **with no authored scenario ID as legacy O1 only**, and only when read from the canonical O1 slot or the explicitly trusted frozen-reference internal route. Do not treat missing identity as O2. For v10–v24, use version-aware proof of authentic O1 provenance; a foreign/explicit conflicting ID always rejects. If missing ID and authenticity cannot be shown, reject rather than guess or repair it. | True old saves must load; ambiguity must not open cross-world contamination. |
| SI-06 | No O2 file, bad O2 file, or O2 .bak may ever cause automatic fallback into the O1 file. The presence or failure of one slot must not change the other slot or its UI availability. | Independent histories. |

**Identity semantics:** the selected chapter, file-path slot, explicitly saved chapter ID (when the format supports it), scene/definition identity and nested management identity must agree. Tree IDs may happen to coincide between distinct worlds; uniqueness is enforced **within** the saved forest and may not be used to infer membership. A real per-world ID/generation token is an open design question, **not** silently adopted here. Retain stable in-forest IDs/history within a slot. A copied O1 v1–v9 file in O2's path is rejected for lack of O2 identity.

## 5. Pre-mutation load, lifecycle and transaction contract

**FR-01 — One trusted decision boundary.** Every load path, including F9, F10, startup Continue, a future O2 selector, and the public LoadData API, MUST pass the same version-aware expected-scenario check plus the existing ForestSaveValidation/FindLoadProblem checks **before any world or scene mutation**. UI CanLoad must match Load's result; revalidate on click to handle file changes. A direct LoadData call must not bypass the protection.

**FR-02 — Correct validation order.** First resolve a fixed slot from the selected chapter; read raw bytes (do not mutate), parse with strict schema/identity presence safeguards, classify historical provenance and version, reject unknown/newer versions unless separately supported by an explicit reader; check slot, identity, scene target/definition, duplicate IDs and ecological/saved-state integrity, and any required species registrations. Only then commit to that target world. Validation may allocate temporary objects but MUST NOT modify live game state or written files. The present best-effort future-version behaviour is not an acceptable multi-scenario fail-closed contract; report it for the later bounded change.

**FR-03 — Distinguish disk load from trusted preview.** The frozen Reference Future v1 in-memory archive pathway must remain reachable with its authenticated archive ID/definition, v12 status and existing hash checks. It must not route to an O2 disk slot or write archive metadata. Returning from preview must restore the exact captured O1 state. This is a narrow explicit trusted internal restore mode, never an arbitrary bypass offered to player files.

**FR-04 — Atomicity of refusal.** If a selected save is missing, unreadable, malformed, from the wrong chapter, with null/unknown/duplicate conflicting IDs, duplicate tree IDs, incompatible schema/version or non-resolvable species/cells, refuse. Preserve exact pre-request forest geometry, active scene, trees and marks, carried and stored wood, cash, inventory, Work Plan/orders, years/annual reports/objectives/history, browsing, ecology and UI active selection. A refused startup Continue must not prematurely dismiss/close the current screen or change the selected chapter. If later scene transition can fail after preflight, the design must preserve the old world or stage/recover without partial target commit; do not assert transactional scene switching is already implemented.

**FR-05 — Save transaction and slot containment.** Save must capture the selected chapter only and validate intended destination and identity **before** writing its temp file. Keep each .tmp/.bak tied to its own canonical slot, do not cross-copy or delete another slot's artifacts. Maintain the existing write/flush/replace and previous-save backup intent; document platform-specific replace fallback risk and require failure-injection testing. If partial writes or exceptions occur, no success message and no loss of the previously valid slot. No save during reference preview. Avoid automatically replacing a valid file with a default scene just because the chapter selection changed.

**FR-06 — Recovery.** If the primary file is invalid and a .bak exists, present an accurate recovery option **only after the backup independently passes the same version, expected-scenario, content and scene preflight**; never silently load or overwrite it. Keep primary and backup bytes untouched until an explicit user-approved recovery action; recovery must itself use a safe copy/replace and preserve a recoverable original. A stale .tmp must never be treated as the authoritative slot. If both primary and backup are invalid or foreign, fail with no mutation and no destructive cleanup. No cross-slot backup promotion.

**FR-07 — Version/field safety.** Read v1–v24 O1 by historical version conditions (not by defaulting away missing identity); preserve v24 teaching latch, v21 racks, v22 objective history, v23 prescriptions and previous geometry/ecology model semantics. New metadata must not affect the frozen Reference Future v1 world/legacy hash compatibility, existing v12 archive bytes, or old file bytes. JsonUtility unknown-field behaviour must be acknowledged rather than assuming lossless round-tripping: never auto-save a loaded future/unknown version and never strip unrecognised data under a deceptive "safe migration."

**FR-08 — Independent accounting/history.** Capture and restore each scenario's own original start state, current ecological year, annual reports and management-event identity, future/past interventions, income/cost/stock and Work Plan. A return visit must show the same chapter's facts, with no O1/O2 leakage even if tree IDs, year numbers and work-order IDs coincide. O2 Gate 1 must demonstrate actual authored irregular/multi-cohort state and repeated year advancement; not merely the O1 scene presented under a new title.

**FR-09 — Honesty.** Provide distinguishable "no save", "wrong forest", "unreadable/corrupt", "unsupported newer version", "backup available but not automatically used" and "save not committed" states. No misleading "Loaded", "Saved", "Recovered" or O2 complete status on failure.

## 8. Open technical decisions (must be resolved before spec approval or corresponding code task)

1. **O2 ID and authored starting scene/definition:** candidate "scenario-two" is not yet verified as a concrete authored scene ID. Recommended fixed alias O2 ↔ scenario-two, not UI-title parsing; verify actual scenario assets, bootstrap and scene lifecycle on target branch before coding.
2. **Top-level identity representation/schema:** current ForestSaveData has none and JsonUtility defaults obscure omission. Recommended explicit top-level identity plus raw-JSON presence/duplicate-key checks with a deliberate schema bump only if necessary; prototype against real v1, v9, v10, v12, v20 and v24 files, including missing nested ID cases. No archive serialization changes.
3. **Authenticating v10–v24 O1 with missing nested ID:** an omitted key can be indistinguishable from a default set during deserialization. Recommended allow proven historical files under strict O1-only path/version and other structural checks; if an ambiguous or malformed candidate cannot be distinguished safely, reject with a recovery note rather than silently classify it.
4. **Scene transition commit model:** startup currently holds a pre-generated Scenario One scene, not a proven separate O2 world. Recommended choose/validate target chapter before world construction and stage safe transitions; inspect actual scene/bootstrap and testing seams. Do not promise full rollback without a demonstrated mechanism.
5. **Primary-vs-backup recovery:** current TryReadSave mentions .bak but does not use it; File.Replace fallback may not be atomic. Recommended explicit user-driven backup recovery with per-slot identity and failure-injection qualification, no silent substitution; determine platform-specific guarantees from tested runtime.
6. **Direct internal LoadData callers:** Reference Preview's CaptureData/LoadData return is a trusted internal route. Recommended explicit named internal mode and verified archive checks, not an open caller flag; inventory all other direct calls before enforcing identity.
7. **Handling future versions/unknown fields:** current LoadData logs and best-effort loads newer versions. Recommended fail closed for disk loads; define whether archive/internal reader exceptions are needed without weakening old-format support. Verify old fixtures, non-destructive read and unknown-key behaviour.
8. **Existing save file naming on released operating systems:** root is Application.persistentDataPath. Do not hardcode an OS path or auto-relocate; verify desktop persistence/path, overwrites and protections on supported environment during feature qualification.
