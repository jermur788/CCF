## 3. Player workflows

**W-01 — Start a new independent forest (amended #524).** A player explicitly chooses a profile before a new forest is committed: **Existing Scenario One** (historical), **Compact Scenario One** (when approved and available) or **Scenario Two** (when approved and available). The chosen profile supplies the correct authored starting world/definition and active save slot; starting fresh does not delete or overwrite any existing save, and **selecting a profile never writes a save**. O2's and compact's actual scene/setup require separate approved world packets; a label switch alone is insufficient. Making compact the future first-demo default never silently converts an existing historical forest.

**W-02 — Save/continue the selected forest.** Save and Continue/F9/F10 load affect the **currently selected** profile's slot only, with an understandable confirmation before a save replaces that profile's own existing current file. After launch, switching chapters or profiles, or re-entering one, cannot inherit a previously active world's trees, cash, inventory, orders, ecology, annual reviews, elapsed years, teaching evidence or learning/help state. No automatic cross-profile transfer.

**W-03 — Reject a foreign/invalid file (amended #524).** Any file offered under the wrong profile is rejected **before** changing the live world, scene, geometry, money, work plan, tutorial state, timeline, visuals, selection, learning/help prefs or any slot's bytes. This includes a historical O1 file in the compact or O2 slot, a compact or O2 file in the historical slot, and compact↔O2, whether copied or renamed. Give a truthful message naming the expected and found profile where this can be read safely, without claiming recovery or corrupting data.

**W-04 — Historical O1.** Continue/Load accepts valid O1 historical v1–v24 formats by their documented version/legacy rules, including v1–v9 without scenarioOne, pre-v20 Legacy40, v20–v24 Enlarged80 and the frozen v12 Reference Future under its separate trusted preview route. **Amended #524:** the existing newer-version warn/best-effort behaviour for genuine historical files is preserved (FR-07). No on-load rewriting of the source file, archive or protected reference hashes.

**W-05 — Compact Scenario One (new #524, PROPOSED).** A compact forest lives only in its own proposed slot. Its early teaching progress (arrival/assessment, the four genuinely planted G1 orders, the first genuine annual review read) is persisted in the compact save from real work and review events. It is never inferred from the historical rack lessons, the v24 latch or device prefs. Reference Future preview is not offered in the compact profile unless separately approved (FR-12).

**W-06 — Learning and help state (new #524).** Device-global historical lesson/help acknowledgements keep their exact keys and values whatever the player does in compact or O2, including a compact "reset learning" action. Each new profile's acknowledgements live under its own proposed prefix.

## 5. Pre-mutation load, lifecycle and transaction contract

**FR-01 — One trusted decision boundary (amended #524).** **One shared preflight** serves every route: Start/New admission, Continue/CanLoad, Save/F5, F9, F10 load and save, the public LoadData API, Reference preview entry and return, and same-slot backup recovery. It applies the profile-specific identity and version check plus the existing ForestSaveValidation/FindLoadProblem checks **before any world, scene, PlayerPrefs or file mutation**. UI CanLoad must match Load's result per profile; recheck at commitment because the file may change between check and click. A direct LoadData call must not bypass the protection: a public load takes the selected profile and the raw text, or a token produced by the preflight; trusted internal modes are enumerated (FR-03). [PROPOSED]

**FR-02 — Correct validation order (amended #524; replaces the blanket future-version rule).**
1. Resolve the fixed slot from the selected profile (compile-time table; no user input).
2. Read the raw bytes without mutating anything. A missing file means "no save for this profile".
3. Parse raw JSON with duplicate-property rejection (precedent: ForestSaveValidation.Geometry.cs). Malformed or truncated data rejects.
4. **Envelope marker test, before any version rule.** In the historical slot, a present marker (or a raw nested scenarioId other than "scenario-one", per B-03) rejects as foreign. In the compact or O2 slot, an absent marker rejects (for example a renamed historical file).
5. New profiles: every envelope key must be present once, of the right type, and an exact case-sensitive allowlisted value matching the selected profile. The nested scenarioId must equal the envelope chapter.
6. **Profile-specific version policy (FR-07):** strict for compact/O2; historical rules for O1.
7. Existing TryReadSave raw validators, then FindLoadProblem (geometry, cells, trees, species, model 2, spawner). Compact geometry must be explicitly known to a compact dispatcher and never fall through to 40 m / 64 cells or 80 m / 256 cells.
8. Expected scene/definition/geometry for the profile, or a staged switch per B-10.
9. Commit check: the bytes are unchanged since step 2 (or re-run the preflight).

Validation may allocate temporary objects but MUST NOT modify live game state, PlayerPrefs or written files. ~~The present best-effort future-version behaviour is not an acceptable multi-scenario fail-closed contract~~ **(#524 correction):** the present best-effort behaviour is **not acceptable for compact or O2**, and it **is preserved for genuine historical O1** unless a separate decision tightens it (B-05). [PROPOSED]

**FR-03 — Distinguish disk load from trusted preview.** The frozen Reference Future v1 in-memory archive pathway must remain reachable with its authenticated archive ID/definition, v12 status and existing hash checks. It must not route to an O2 or compact disk slot or write archive metadata. Returning from preview must restore the exact captured O1 state **and the active profile**. This is a narrow explicit trusted internal restore mode, never an arbitrary bypass offered to player files. **#524:** preview entry and return run the shared preflight in its trusted-internal mode. The archive is never presented as a compact-geometry future (FR-12).

**FR-04 — Atomicity of refusal.** If a selected save is missing, unreadable, malformed, from the wrong chapter or profile, with null/unknown/duplicate conflicting IDs, duplicate tree IDs, incompatible schema/version or non-resolvable species/cells, refuse. Preserve exact pre-request forest geometry, active scene, trees and marks, carried and stored wood, cash, inventory, Work Plan/orders, years/annual reports/objectives/history, browsing, ecology, UI active selection, **active profile, every learning/help PlayerPrefs namespace and the bytes of all three slots and their sidecars** (#524). A refused startup Continue must not prematurely dismiss/close the current screen or change the selected chapter. If a later scene transition can fail after preflight, the design must preserve the old world, or stage/recover without a partial target commit; do not assert that transactional scene switching is already implemented. A UI check followed by partial LoadData mutation is not conformance.

**FR-05 — Save transaction and slot containment.** Save must capture the selected profile only and validate the intended destination and identity **before** writing its temp file. Keep each .tmp/.bak tied to its own canonical slot, and do not cross-copy or delete another slot's artifacts. Maintain the existing write/flush/replace and previous-save backup intent; document the platform-specific replace-fallback risk and require failure-injection testing. If partial writes or exceptions occur, there is no success message and no loss of the previously valid slot. No save during reference preview. Avoid automatically replacing a valid file with a default scene just because the selection changed. **#524:** historical saves keep byte-identical serialization (`JsonUtility.ToJson(data, true)`, no envelope). Compact/O2 saves write the envelope. Whether F5 should gain the same replace confirmation the F10 save already shows is an owner UX question (Q-03).

**FR-06 — Recovery.** If the primary file is invalid and a .bak exists, present an accurate recovery option **only after the backup independently passes the same profile identity, version, content and scene preflight**; never silently load or overwrite it. Keep primary and backup bytes untouched until an explicit user-approved recovery action; recovery must itself use a safe copy/replace and preserve a recoverable original (any extra preserved-original filename is a new literal: [BLOCKED B-09]). A stale .tmp must never be treated as the authoritative slot. If both primary and backup are invalid or foreign, fail with no mutation and no destructive cleanup. No cross-slot backup promotion.

**FR-07 — Version/field safety (amended #524; profile-specific).**

Read v1–v24 O1 by historical version conditions, not by defaulting away missing identity, and preserve all previous geometry/ecology model semantics. New metadata must not affect the frozen Reference Future v1 world/legacy hash compatibility, existing v12 archive bytes, or old file bytes. JsonUtility unknown-field behaviour must be acknowledged rather than assuming lossless round-tripping: never auto-save a loaded future/unknown version, and never strip unrecognised data under a deceptive "safe migration". The historical best-effort path stays a load-only behaviour.

**FR-08 — Independent accounting/history.** Capture and restore each profile's own original start state, current ecological year, annual reports and management-event identity, future/past interventions, income/cost/stock and Work Plan. A return visit must show the same world's facts, with no O1-historical / O1-compact / O2 leakage even if tree IDs, year numbers and work-order IDs coincide.
