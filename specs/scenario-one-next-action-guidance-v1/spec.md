## Product intent and problem

The user's complaint is: Objective 1 needs more detail and a diagram that looks like the Stand Map, not abstract rows of text. The contextual call to action should highlight the Stand Map from the Objectives screen, and then Plan Racks on the map, instead of a generic “Back to forest” button. Always highlight the next logical enabled action as the objective progresses, rather than the default close button.

No ecological research claim is introduced: five racks and 16–20 m are site-specific teaching/gameplay calibration, not universal forestry recommendations. ## PROPOSAL — functional requirements

**FR-1 Single cue.** Derive one transient presentation result (action target, visible verb, reason, enabled state) from existing current lesson, rack confirmation/count, entrance marks, rack-owned work status and existing availability validators. Reuse TeachingFacts/CurrentTopicIndex and candidate RackV2Instruction after base reconciliation. Keep GuidedTopicIndex/NextCueStep for their existing optional-practice purpose; do not build a second progression engine. Exactly one enabled primary action in the active interaction scope, except FR-2’s safe no-primary modal case. A pending modal/confirmation owns that scope and suppresses background primary emphasis and background cue activation on every screen; it does not add a second primary. Other controls remain secondary. Re-evaluate after edits, confirmation, reopen, marking, approval, resolution, screen entry and load. Optional credits cannot skip required forest work.

**FR-2 Cross-screen precedence.** Before any planning or lesson row, resolve the active modal/confirmation scope: `editor.ConsentPending` → `editor.ResetPending` → `reopenPending` → any other blocking modal. These states always outrank background planning, confirmation, marking and Work Plan cues, even when the background row also matches. If several are pending, use that fixed order; for other nested modals use the topmost active modal. Never nominate an action behind a modal. Recompute from current state only after the prompt is dismissed; never retain a cached background cue. Apply the following first matching row only within that rule; navigation requires explicit player activation. Opening Stand Map MUST NOT automatically enter planning, confirm, approve, mark or advance time.

| Derived condition | Objectives primary | Stand Map / destination primary |
|---|---|---|
| `editor.ConsentPending` | Suppress background cue; active prompt owns primary | Keep approved work (`map-consent-decline`) |
| `editor.ResetPending` | Suppress background cue; active prompt owns primary | Keep my racks (`map-edit-reset-cancel`) |
| `reopenPending` | Suppress background cue; active prompt owns primary | Keep the plan confirmed (`map-reopen-decline`) |
| Other blocking modal | Suppress background cue; active modal owns primary | Existing safe cancel/close; if none is available, show modal reason without a primary rather than nominate a background action |
| V2 plan unconfirmed; planning not active | Open Stand Map [M] (`ShowMap`) | Plan Racks (`map-plan-rack`, ToggleRackMode; no dedicated key found) |
| Planning active; count differs from five or five is invalid | Open Stand Map [M] | Use FR-3’s ordered selection; guidance focuses the existing instruction and validator reason; disabled Confirm retains its reason |
| Exactly five; CanConfirmRackPlan true; no pending consent | Open Stand Map [M] | Confirm Rack Plan (`map-rack-plan-confirm`, ConfirmRackPlanFromCard → ConfirmRackPlanFromMap); button activation, no dedicated shortcut found |
| Confirmed; entrances marked below target | Return to forest to mark entrances (`CloseAll`) | Return to forest to mark entrances; explain P spray marker, aim within 3.5 m and left-click (candidate wording F2) |
| Entrances complete; rack-owned pending work | Review Work Plan [Tab] (`ShowWorkPlan`) | Work Plan navigation; within plan highlight existing approval only when its validator permits, retaining cost/all-pending-work warning |
| Rack work approved, awaiting resolution | Open Work Plan [Tab] | Existing Advance one year only when permitted; retain existing review gates |
| Work resolved | Existing lesson's review/inspection action | Follow TeachingFacts and existing lesson instruction; do not keep pointing at Plan Racks |

Reopened plans return to planning precedence; preserve stored entrance marks and harvested locks. Non-V2/Legacy40 uses existing legacy lesson and controls; never offer unavailable V2 planning. Later lessons follow the same single-primary rule using existing enabled actions; concrete later-lesson mapping needs Manager acceptance before dispatch (Q3).

**FR-3 One instruction source and deterministic fallback.** Evaluate one snapshot in this order:

1. Resolve FR-2 modal precedence first; safe prompt choices override background instructions for the primary cue. Background lesson text may remain context but must not be presented as an actionable “Next:” instruction while a prompt owns interaction. Never auto-focus or execute destructive consent/reset/reopen acceptance.
2. Outside a prompt, select the existing lesson with TeachingFacts/CurrentTopicIndex. For V2 Objective 1, candidate `RackV2Instruction(counter, confirmed, marked, target, workPending)` (`LearningObjectivesView.Curriculum.cs:98–104` at **72b4efbd1c653fa2231f632a79030a83ff76f833**) is authoritative for the next stage and displayed imperative: unconfirmed → map planning/confirmation; confirmed with incomplete entrances → forest marking; entrances complete → Work Plan review/approval when pending, otherwise annual advance. FR-2 projects the first unfinished step of that instruction onto the current screen (Open Stand Map → Plan Racks → Confirm); it cannot choose a competing stage. Reuse helper wording verbatim; select targets using the same arguments, never by parsing its text. After Objective 1 resolves, existing current-lesson instruction wins. If the chosen base lacks the helper or helper and facts disagree, stop for Q4 reconciliation rather than adding a second instruction source.
3. Check the existing availability validator for that target. If enabled, use it. If blocked, retain the helper instruction as context and append the existing validator reason. Do not substitute a different progression imperative or skip prerequisites.
4. Choose a corrective action only from this ordered allowlist, first eligible wins: (a) Open Stand Map when unconfirmed planning is next and the map is not active; (b) Plan Racks when that map is active and planning is off; (c) Undo last rack edit (`map-edit-undo`) only when the current blocking reason is the latest refused/invalid edit and `CanUndoRackEdit` permits it; (d) Delete rack (`map-edit-delete`) only when over the five-rack target and the already selected rack is editable/unlocked. Each must be enabled, in the active scope, and directly address that reason. Never infer eligibility from free-text reason wording: use the validator/state condition; if no unambiguous condition exists, skip the corrective action. Do not auto-select a rack, offer reset as a correction, or enumerate arbitrary enabled controls. Fixed allowlist order resolves all ties.
5. If no eligible correction exists, use one enabled “Read next-step guidance” action to focus/reveal the existing helper instruction plus validator reason and help; the planning row uses this same action. It supplies no new imperative or mutation. Missing required services/state instead produces “Guidance unavailable — reopen Objectives” with one safe Close action. If a modal has no safe enabled choice, step 1’s no-primary exception wins over this fallback.

Ordinary Back to forest stays secondary unless the authoritative instruction requires forest activity or no guidance can be supplied. Do not invent validity or bypass existing gates, including known MFM validity limitations. The corrective allowlist is a proposed presentation policy, not a claim that validators currently expose every needed structured reason; ambiguous reasons fall back to existing guidance without backend changes.

**FR-4 Detail.** Objective 1 must explain permanent extraction access, five-rack target, site-specific advisory 16–20 m spacing, standing rows retained, and the separate plan → confirm → physically mark entrances → review/approve → annual execution stages. Reuse V2 instruction and derived counter verbatim where applicable. Confirmation creates pending work; approval commits work; successful annual resolution opens corridors. Counter and primary action must describe the same snapshot.

**FR-5 Faithful map-like illustration.** Replace only Objective 1's abstract teaching picture with a passive north-up stand-shaped map illustration. Recommended static teaching example: current approved five parallel racks connected to the existing headland, inside the actual stand boundary, with recognisable canopy/tree crowns and existing access path, grid, north and scale conventions. Reuse map transform/symbol definitions rather than hand-inventing a palette. Show five labelled R1–R5 planned corridor bands, entrance squares at headland, retained planted rows between corridors and a labelled perpendicular spacing bracket. Do not draw five abstract text rows. Retain canopy inside planned corridors: planned lines overlay trees, not holes/stumps. Show the round handle only in an explicitly labelled selected-rack example. Legend must say “Illustration of a proposed layout — not your saved plan. Planning clears nothing.”

Geometry must come from the approved reference layout at the eventual implementation base; verify boundaries, rack widths, actual headland side and spacing before drawing. Seven standing rows is the legacy authored example (F2), not a universal invariant of editable V2 racks: depict/count it only if the chosen reference supports it; otherwise label retained rows without a false count and seek Q2 decision. The figure may imply access intent, relative direction and retained canopy. It MUST NOT imply planned routes are cleared, confirmed, approved, executed or machine-qualified; no proposed diagonal 3+2 spine, automatic removal marks, or new access connection. A metric scale is allowed only with verified metric geometry; otherwise explicitly “schematic, not to scale”. Planned/harvested styles remain distinct. This scope produces a diagram specification, not an image asset.

**FR-6 Accessibility.** Primary emphasis uses “Next:” text, border/weight and visible focus indicator as well as colour. All symbols have shape/pattern plus written legend and text equivalent describing headland, five racks and retained rows. At 1280×720 and 1920×1080 preserve readable body/legend text (target at least 16 physical pixels), no clipped CTA/reason/counter, and scroll access to full explanation. Allow diagram below words at narrow width; never shrink labels to illegibility. Proposed focus order: next enabled action, remaining navigation, objective content/help, secondary close. Enter/Space activate buttons; Esc retains safe exit; no focus stealing during live refresh. Explicit navigation may place focus on next destination control; no automatic navigation or cursor movement. Tab conflicts with Work Plan shortcut (F8): Q1 must select a scoped navigation policy before implementation. Added guidance controls and all flow destinations must be keyboard reachable; full rack geometry editing is not claimed accessible by this draft and needs a separately agreed solution/scope if required for end-to-end keyboard-only play.
